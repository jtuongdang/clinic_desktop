## Formatting examples and bounded proposal

The examples below are **symbolic placeholders**, not phone values. Let `P` be one supported prefix digit in `{3, 5, 7, 8, 9}` and `D…` stand for the remaining digits.

| Case | Current behavior | Bounded proposal (not approved) |
|---|---|---|
| National prefix | A newly written value has separators removed but keeps `0`. A search token such as `0 P·D…` retains its separators; because SQL uses that literal token in a substring predicate, this formatting difference is not normalized and a match is not guaranteed. | In the SĐT criterion only, remove the already-supported whitespace, dot, and hyphen separators, validate the full value, and compare the normalized query to the primary phone value. `0P D…`, `0P·D…`, and `0P-D…` then represent one same-prefix criterion. |
| Country-code prefix | A stored value keeps `+84`; a search token with spaces/dots/hyphens is likewise passed through as entered. | Apply the same separator removal to `+84 P D…` / `+84P·D…` / `+84P-D…`, preserving `+84` and matching only the same `+84` primary-phone value. |
| Prefix conversion | Persistence does not convert `0` to `+84` or vice versa. Current search compares the raw substring; a full token under one prefix does not establish a match to a stored value under the other prefix. | Do not convert prefixes or claim that the two forms are search-equivalent. Limit this proposal to separator equivalence under the same prefix. |
| Both inputs populated | UI makes a separate generic substring query for each nonblank input and unions/deduplicates results by patient ID. Each generic token can match any of the six SQL fields, not just the input’s label. | Preserve the two existing controls and additive union/deduplication behavior. Classify the phone input before normalization so separators are never stripped from CCCD or name/code criteria; keep every query behind the same guard, audit, and SQL scope. |

This proposal narrows the SĐT field to a complete supported primary-phone value and exact same-prefix equivalence. It does **not** propose searching the emergency-contact number, normalizing arbitrary text, expanding role/scope, changing the visual layout, or changing the CCCD control. If partial phone search is a required behavior, that needs an explicit choice before implementation because the present SQL treats all keywords as substrings.

## Unresolved policy and status

- **Prefix equivalence:** Owner-approved persistence preserves `0` and `+84` without conversion; whether a search entered with one prefix should find a stored value with the other is a separate, unresolved search policy. This report does not imply equivalence.
- **Legacy stored values:** the Owner decision says no backfill. Whether to support both raw legacy separator layouts and newly canonical values in search without a data migration remains unresolved. Current literal substring SQL can behave differently for those rows; this report does not propose a migration or silent rewrite.
- **Partial numbers / emergency contact:** the proposed bounded contract assumes full primary-phone input. Partial matching and searching the optional emergency contact are not decided.
