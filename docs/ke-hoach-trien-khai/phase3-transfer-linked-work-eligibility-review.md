# VIS-TRANSFER-LINKED-WORK-01 — Linked-work eligibility source review

**Status:** Report-only review of the approved `VIS-TRANSFER-SOURCE-RECON-01` contract. Snapshot: 2026-11-06. No code, schema, policy, database, or patient data changed or accessed.

## Executive finding

The schema can represent service orders/results, prescriptions/dispensing, and invoices/receipts/debt linked to a visit. Domain models expose some state and lifecycle methods, but the reviewed checkout has no Application use cases or Infrastructure persistence adapters for these linked-work areas. Consequently, schema fields are not evidence that the current application can load a complete, current, transactionally consistent eligibility snapshot. Transfer must remain default-deny until that source is implemented and verified.

Preserve the approved policy: linked records stay attached to the same visit; transfer does not cancel or mutate them, perform billing, or create charges. Pending work may follow only when a reliable source proves it is safe and its performing unit and responsibility remain intact. Issued prescriptions, confirmed results, and posted financial transactions are immutable; adjustments require a separate authorized, reconciled, audited process. The current model/schema does not consistently identify those immutable boundaries, so do not infer them from status names alone.

## Applying the approved transfer rules

| Owner rule | Required transfer behavior from these sources |
|---|---|
| Preserve attachment | Keep the visit ID and all existing links unchanged: service orders and prescriptions retain `maLuotKham`; results remain under their existing order; invoice, lines, receipts and debt remain under their existing invoice. Do not reparent or copy artifacts. |
| No auto-cancel or linked-work mutation | Do not call status setters, delete/soft-delete, issue/dispense, or result/payment operations as part of transfer. Preserve even already-cancelled rows; their status does not establish that no result or charge exists. |
| Pending work may transfer only if safe | The approved rule permits pending work to follow only when a reliable source proves it is safe and responsibility remains intact. Technical recommendation only—not an Owner-approved state rule: a future eligibility check could consider an order only when it is explicitly pending, has no execution/result, and its performing room/clinician and unchanged responsibility are verified; it could consider a `TAM` prescription only when dispensed quantities are zero, no linked issue voucher/inventory movement exists, and pharmacy ownership/location is resolved. Treat `DA_TIEP_NHAN`, `CHO_KET_QUA`, `DA_DUYET`, partial dispensing, missing owner/location, or inconsistent evidence as requiring block or explicit completion/handoff unless an Owner-approved lifecycle contract says otherwise. These candidate states and gates are proposals, not approved transfer-state rules. |
| Issued prescriptions, confirmed results and posted financial transactions are immutable | Preserve their identity, status, values, timestamps and ownership. Current code has no reliable “issued,” “confirmed,” or “posted” flag for all three categories; treat any issue/result/receipt evidence as immutable and do not infer a reversible state. An unclear boundary requires block/handoff. Any correction is outside transfer and needs the separately authorized, reconciled, audited path. |
| No billing mutation / no duplicate charge | Transfer must not create an invoice, invoice line, receipt, refund, debt entry, or payment event; it must not recompute or modify existing amounts/statuses. Since invoice-line source references are polymorphic and lack a source FK/uniqueness guarantee, ambiguous lines or duplicate-charge provenance cannot be normalized by transfer: stop for billing reconciliation. Verify that transfer code has no billing side effects and that retry cannot repeat a charge. |
| Transaction consistency and optimistic concurrency | Eligibility reads and visit mutation must share the approved transaction boundary; revalidate linked-work status/ownership and visit version before commit. Any missing dependency, query failure, unknown status, inconsistent FK/soft-delete evidence, stale version, or incomplete result must return failure without a location/queue mutation. Do not treat query failure or an absent adapter as an empty linked-work set. |

## Technical recommendation: eligibility dependencies and default deny

Technical recommendation, not an Owner-approved state rule: before enabling transfer, implement a transactionally consistent source that, for the exact visit, can enumerate **all** service orders and result children; prescriptions and every line; linked dispense vouchers and inventory movements; and every invoice, line, receipt, and debt record. It should include status, `isDeleted`, version, timestamps and relevant ownership/location fields, validate parent-child links, decode statuses without fallback, and expose failures distinctly from “none found.” The service-order query should resolve the performing unit and responsible clinician; prescription/stock reads should resolve dispensing location and issue state. Billing eligibility should resolve all invoices and reconcile source lines/receipts without creating or changing financial artifacts.

Preserve the approved fail-closed requirement: **deny transfer whenever linked-work eligibility cannot be proven**, including a missing repository/handler, empty-shaped fallback, unknown/mismatched status, partial or soft-deleted evidence that prevents reconciliation, unassigned pending work, result/issue/payment evidence without a reliable finality state, multiple/ambiguous invoice results, or dependency/concurrency failure. Unknown or mismatched statuses must fail closed; do not infer eligibility from them. A verified empty linked-work set or a fully identified safe pending handoff may be considered only by a later implementation under the approved contract; this review authorizes neither.
