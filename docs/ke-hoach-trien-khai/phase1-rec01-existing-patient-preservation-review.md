## Handler and persistence semantics

- Existing-patient status is inferred from a positive command patient ID. Handler enforces scoped lookup, then updates rather than inserts; an out-of-scope/missing record is denied. [`RegisterPatientHandler.java:64-99,102-103`](../../clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterPatientHandler.java)
- Patient UPDATE writes the form command's demographic columns and uses `WHERE id=? AND version=? AND isDeleted=0`; success increments `version`. A concurrent write after the handler's read should therefore fail the compare-and-set. [`BenhNhanRepositoryImpl.java:181-201,312-320`](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/BenhNhanRepositoryImpl.java)
- **Confirmed stale-form risk:** the form-generated patient has no selected-record version, and handler replaces its version with the latest database version before UPDATE. Thus a command based on an older form snapshot can still pass the repository version check and overwrite newer fields if no other write occurs after this handler's fresh read. The same read-current-version-then-update pattern applies to insurance. Interleaving behavior is inferred from the source; no concurrent integration test was run.
- **Unverified target behavior:** this review did not connect to SQL Server or inspect a live schema. SQL and mapping findings are based on checked-in source and migrations only.

## Regression matrix required for acceptance

All cases should use synthetic fixtures and stay off `clinicDb`.

| Case | Expected behavior | Current baseline evidence |
|---|---|---|
| Select/save patient with non-null `maTinh`, `maHuyen`, emergency contact name and phone | Preserve all hidden values unless the user explicitly edits them. | Current form omits them and patient UPDATE binds them: confirmed failure. |
| Select/save a patient whose gender is `GioiTinh.O` | Keep `O` through form and command, or provide an explicit supported choice; never silently convert to `M`. | Confirmed failure (`selectPatient` and command mapping). |
| Select/save legacy ethnicity, nationality and residence combo values not in current option lists | Keep exact value in display and command, or surface a deliberate validation choice; never silently coerce to a different value. | Fallback exists in source, but no focused round-trip test; unverified. |
| Existing patient with insurance, command/form has no card or blank card number | Existing card remains unchanged and is not mistaken for deleted; UI must not imply deletion unless explicit delete behavior is added. | Handler skips persistence without a number; existing tests cover only a new patient with omitted insurance, not existing-card preservation. |
| Existing non-BHYT insurance card with a nonblank number | Preserve its `loaiBaoHiem` while editing represented fields, or explicitly support choosing its type. | Confirmed baseline type-loss path; no focused `BaoHiemRepositoryImpl` test was found in the inspected test sources. |
| Edit one represented patient/card field (e.g. phone/address or expiry/benefit rate) | Persist the intended edit while preserving all untouched/hidden values and unrelated card fields. | Existing form test covers representative extraction; synthetic patient repository tests cover patient map/bind fields. End-to-end hidden-field preservation is not covered. |
| Submit an old form snapshot after another update | Reject/reconcile stale data or merge against the intended field-level contract; do not silently overwrite newer edits. | Handler refreshes version from persistence before UPDATE; stale-snapshot overwrite risk is confirmed by source, not exercised by a concurrency test. |
