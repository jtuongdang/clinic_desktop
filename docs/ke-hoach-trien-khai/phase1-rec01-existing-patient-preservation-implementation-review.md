## Stale-form / version risk

**Residual risk (confirmed by source; not exercised by a test).** The form-generated patient contains an ID and current field values, but does not carry the version observed when that patient was selected ([panel command construction, lines 650–679](../../clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/components/PatientRegistrationFormPanel.java#L650)). On submission, the handler fetches the latest in-scope patient, overlays the older command's represented fields, and updates it ([handler, lines 85–93, 142–161](../../clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterPatientHandler.java#L85)). Insurance follows the analogous latest-card lookup and form overlay ([handler, lines 104–112, 163–180](../../clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterPatientHandler.java#L104)).

The repository's `WHERE id=? AND version=?` compare-and-set detects a write that races **after the handler's fresh read** ([patient UPDATE, lines 181–201](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/BenhNhanRepository.java#L181); [insurance UPDATE, lines 75–98](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/BaoHiemRepository.java#L75)). It does not detect that the form itself was based on an older snapshot: if another update commits before this handler's read, the handler reads the newer version, then may overwrite its represented fields with stale form values and successfully write using that fresh version. The same limitation applies to insurance fields. Thus optimistic locking remains useful for the read/write race but is not a stale-form/version guarantee.

**Disposition:** Track stale-form conflict detection/reconciliation as a separate follow-up; it does not block this narrowly scoped preservation implementation because the reviewed change preserves unrepresented persisted fields and the stated acceptance does not add a form-origin version contract. It must, however, block any broader claim that an old open form cannot overwrite newer represented-field edits. If REC-01 is intended to promise stale-form rejection, that requirement needs an explicit contract and implementation before claiming it.

## Overall conclusion

Compared with the baseline, the prior confirmed hidden-field clearing and gender coercion are addressed; existing-card omission and non-BHYT type preservation are covered at the handler boundary, and legacy combo handling now has focused round-trip/reset coverage. The two earlier follow-up gaps have been addressed: `BaoHiemRepositoryTest` (`10/10` synthetic JDBC tests PASS) was added in commit `563f4d6` (task `1a2d14bf`), and the legacy `maNoiSong` residence combo reset test on patient switch/clear was added in commit `2efc3a6` (task `b58dc6e5`). The remaining review note is the stale-form residual risk. Findings are based on checked-in source and synthetic tests only; no SQL Server/`clinicDb` behavior was verified. No REC-01, PAT-02, or SEC-01 gate closure is asserted.
