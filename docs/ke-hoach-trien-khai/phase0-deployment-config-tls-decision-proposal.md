# Phase 0 packaged-JAR configuration and SQL Server TLS decisions

**Status: decision proposal only — all choices below require Owner approval.** Prepared under approved contract [REC-SESSION-INVALIDATION-AND-PHASE0-DEPLOYMENT-DECISIONS-01](phase0-db-config-resolution-contract.md), contract ID `f62a4f45-b4bb-4076-8064-af608dfe2963`. This document changes no implementation, configuration, runtime behavior, or readiness status. It does not select an external path, secret source or precedence, TLS policy, or `trustServerCertificate` value.

## Current evidence

- [`DatabaseConnection`](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/DatabaseConnection.java) reads only the classpath resource `db.properties`; it has no external-path argument or adjacent-file lookup. It samples environment variables through `System.getenv`.
- [`DatabaseConfiguration`](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/DatabaseConfiguration.java) resolves classpath property values as the split-field base, then replaces each with its nonblank `DB_URL`, `DB_USERNAME`, or `DB_PASSWORD` counterpart. The environment full string `DB_CONNECTION_STRING`, when nonblank, wins over those split fields. Split environment overrides are trimmed; the full string is preserved as supplied. Configuration is loaded lazily once. Programmatic `setConnectionString` can supersede the environment full string; `configure` replaces split fields without clearing the programmatic full string.
- The [desktop Shade configuration](../../clinic-desktop/pom.xml) excludes the `db.properties` archive entry. The [example properties file](../../clinic-infrastructure/src/main/resources/db.properties.example) is a development template, not proof of a packaged-JAR config source. The [README](../../README.md) describes environment variables for JAR use and copying the example for IntelliJ, but does not establish a separately discovered external properties file. The [operations runbook](../OPERATIONS_RUNBOOK.md#3-database-configuration-and-secret-handling) explicitly records that adjacent external-file discovery is not implemented/proven and packaged-JAR launch has not been validated.
- The example URL includes `encrypt=true;trustServerCertificate=true`. The resolver passes the selected URL through; it does not add TLS options or establish certificate behavior for URLs without them. **The sample `trustServerCertificate=true` is not approved policy.** The runbook says deployment TLS/certificate validation and runtime secret injection remain open.
- Existing synthetic tests cover resolver source precedence, presence-only `toString()` output, connection-overload selection, and generic connection-test diagnostics ([`DatabaseConfigurationTest`](../../clinic-infrastructure/src/test/java/vn/clinicmanagement/infrastructure/persistence/DatabaseConfigurationTest.java), [`DatabaseConnectionTest`](../../clinic-infrastructure/src/test/java/vn/clinicmanagement/infrastructure/persistence/DatabaseConnectionTest.java)). They do not prove packaged-JAR external configuration resolution or a SQL Server TLS handshake.

## Decisions for Owner

### Packaged-JAR configuration discovery

| Option for decision | Operational and security tradeoffs |
|---|---|
| **Process environment only**: use the already-read split `DB_*` values or `DB_CONNECTION_STRING`; arrange injection outside the JAR. | No new file-discovery behavior and avoids putting secrets in the artifact. Depends on a controlled launcher/secret injector, careful environment access, and a defined rotation/restart process. The existing resolver supports the input, but packaged-artifact resolution and the launch recipe still need test evidence. |
| **Explicit external properties file**: add a deliberate path input (for example, an approved command-line/system-property/environment path) and read only that file. | Makes a file-based deployment possible with explicit operator intent and avoids ambiguous working-directory behavior. Requires Owner decision on path mechanism, permissions/ownership, missing/unreadable-file behavior, and whether values may contain secrets. A readable file can be copied or backed up, so access controls and rotation matter. No such mechanism currently exists. |
| **Implicit adjacent-JAR or working-directory discovery**: search a conventional location without an explicit path. | Convenient, but launch-directory and symlink/location ambiguity can load unintended configuration; operators may not know which file won. Requires a precise, observable search order and failure behavior. Not implemented or documented as a supported path. |

For any chosen discovery mechanism, decide whether property values may contain credentials, whether a file may provide only non-secret settings while secrets come from another source, how unreadable/malformed input behaves, and how the selected source is identified safely without logging values. No filesystem path is approved here.

### Secret provision and precedence

| Option for decision | Operational and security tradeoffs |
|---|---|
| **Split environment values** (`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`) supplied by the approved process/secret-injection mechanism. | Secrets can be injected independently of the artifact and rotated through the operating environment. Requires secure environment handling and restart semantics; the current code permits URL-only authentication and does not require a complete username/password pair. |
| **Full environment connection string** (`DB_CONNECTION_STRING`). | Fits JDBC options and credentials into one input, and is already supported. It is harder to inspect/rotate individual values and must never appear in logs, diagnostics, or process output. The current resolver gives a nonblank full environment string precedence over split environment values. |
| **External properties file** for some or all values, if file discovery is approved. | Familiar for local operations, but secrets persist in a file and need restrictive access, backup/rotation controls, and a defined precedence relative to environment values and the full connection string. The current loader cannot read a file outside the classpath. |
| **Mixed settings**: non-secret URL/options from a file and credentials from environment or an approved secret injector. | Can separate operational settings from credentials, but only if conflict rules are explicit and credential sources cannot unexpectedly override each other. Requires tests for every supported combination. |

Owner approval must define an exact precedence table across properties, split environment variables, `DB_CONNECTION_STRING`, and any future explicit programmatic override. Existing behavior above is evidence, not an endorsement of that ordering. Decide supported authentication combinations (including URL-only and partial credentials), whether blank means “ignore” or “clear,” and what happens on malformed or unreadable configuration. Do not infer a new source or precedence from current behavior.

### SQL Server encryption and certificate validation

| Option for decision | Operational and security tradeoffs |
|---|---|
| **Require encrypted transport and validate the server certificate and identity** using the deployment's approved trust chain and hostname. | Provides encryption plus peer authentication when certificate chain and name are valid. Requires certificate provisioning/renewal and compatible JDBC driver/runtime trust configuration. The exact JDBC options, trust-anchor source, and hostname rule must be approved and tested. |
| **Encryption with certificate validation bypassed** (the sample's `trustServerCertificate=true` is one example). | May simplify isolated development with an untrusted/self-signed certificate, but removes server-certificate validation and permits connecting without verifying server identity. This is not established by the sample and is **not approved policy**; Owner must explicitly decide whether any bounded non-production exception is acceptable. |
| **Rely on driver defaults or omit TLS options from the URL**. | Reduces explicit configuration, but effective encryption and validation may vary by JDBC driver version and server settings. Requires version-pinned behavioral evidence; omission alone is not evidence of a safe policy. |

Owner must decide whether encryption is mandatory, the certificate trust and hostname-validation model, treatment of invalid/expired/untrusted certificates, and whether any environment-specific exception is allowed. No `trustServerCertificate` value is selected or approved in this proposal.

## Acceptance evidence after approval

Run only in an authorized isolated environment with synthetic values and no production connection. First implement the approved contract separately; this proposal itself does not request or perform these changes.

1. **Packaged artifact and source resolution:** Build the shaded JAR and inspect its entries to verify `db.properties` is absent. Launch a no-network test using a fake/injected configuration source for the Owner-selected mechanism. Assert that the selected synthetic URL and authentication mode reach the expected resolver/JDBC handoff; assert configured source and precedence for conflicting synthetic values. If an external file is approved, test the exact documented explicit path and prove an unrelated adjacent file is not selected unless that behavior was approved.
2. **Secret redaction:** Use distinct synthetic markers for password and full connection string. Assert none occur in resolver/target string representations, validation errors, thrown exceptions, stdout/stderr, or captured application diagnostics. Assert logs identify neither secret source contents nor full JDBC URL if it embeds credentials.
3. **Invalid-configuration fail-fast:** For each Owner-defined invalid case (at minimum missing required URL and any rejected partial-credential combination), assert a clear safe error occurs before the fake connection factory/driver is called (zero handoff calls). Verify unreadable/malformed selected-source behavior matches the approved fail/ignore policy and leaks no synthetic markers. Do not attempt a real connection.
4. **TLS option boundary:** Assert the exact approved SQL Server encryption/certificate options are present in the selected synthetic JDBC configuration and that no default or `trustServerCertificate` value is silently inserted when absent. Check all approved input-source combinations, including full connection string versus split URL, for consistent policy enforcement.
5. **Controlled TLS handshake:** Only after separate authorization, use a named synthetic SQL Server endpoint and the pinned JDBC driver/runtime. Record outcomes without credentials: valid trusted certificate and matching identity succeeds; untrusted/expired certificate and hostname mismatch fail when validation is required; any approved exception behaves only in its explicitly bounded environment. Include encryption negotiation evidence. Never treat a successful connection using `trustServerCertificate=true` as certificate-validation evidence.

Until the Owner records the discovery mechanism, secret source/precedence, authentication validation, and TLS/certificate choices—and the corresponding acceptance evidence is produced—these Phase 0 deployment decisions remain open. This proposal is not deployment readiness evidence.
