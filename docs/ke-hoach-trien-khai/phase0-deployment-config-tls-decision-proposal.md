## Current evidence

- [`DatabaseConnection`](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/DatabaseConnection.java) reads only the classpath resource `db.properties`; it has no external-path argument or adjacent-file lookup. It samples environment variables through `System.getenv`.
- [`DatabaseConfiguration`](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/DatabaseConfiguration.java) resolves classpath property values as the split-field base, then replaces each with its nonblank `DB_URL`, `DB_USERNAME`, or `DB_PASSWORD` counterpart. The environment full string `DB_CONNECTION_STRING`, when nonblank, wins over those split fields. Split environment overrides are trimmed; the full string is preserved as supplied. Configuration is loaded lazily once. Programmatic `setConnectionString` can supersede the environment full string; `configure` replaces split fields without clearing the programmatic full string.
- The [desktop Shade configuration](../../clinic-desktop/pom.xml) excludes the `db.properties` archive entry. The [example properties file](../../clinic-infrastructure/src/main/resources/db.properties.example) is a development template, not proof of a packaged-JAR config source. The [README](../../README.md) describes environment variables for JAR use and copying the example for IntelliJ, but does not establish a separately discovered external properties file. The [operations runbook](../OPERATIONS_RUNBOOK.md#3-database-configuration-and-secret-handling) explicitly records that adjacent external-file discovery is not implemented/proven and packaged-JAR launch has not been validated.
- The example URL includes `encrypt=true;trustServerCertificate=true`. The resolver passes the selected URL through; it does not add TLS options or establish certificate behavior for URLs without them. **The sample `trustServerCertificate=true` is not approved policy.** The runbook's statement that TLS/certificate validation remains open predates the 2026-11-06 Owner decision below; the decision now establishes the mandatory policy, while implementation details and evidence remain outstanding.
- Existing synthetic tests cover resolver source precedence, presence-only `toString()` output, connection-overload selection, and generic connection-test diagnostics ([`DatabaseConfigurationTest`](../../clinic-infrastructure/src/test/java/vn/clinicmanagement/infrastructure/persistence/DatabaseConfigurationTest.java), [`DatabaseConnectionTest`](../../clinic-infrastructure/src/test/java/vn/clinicmanagement/infrastructure/persistence/DatabaseConnectionTest.java)). They do not prove packaged-JAR external configuration resolution or a SQL Server TLS handshake.

## Owner decisions — PHASE0-DB-DEPLOY-DECISION-RECON-02

**Decision date: 2026-11-06.** The following are approved policy requirements, not implementation authorization.

### Packaged database configuration

- **Approved source coverage:** the packaged desktop must support both process environment/secret injection and an external properties file selected through an explicit path/interface.
- **Not approved:** implicit discovery beside the JAR or from the current working directory. No implicit path selection is authorized.
- **Still unresolved for configuration:** the explicit file path/interface; precedence and conflict handling among supported sources; how settings and secrets are split between sources; and behavior for a missing, unreadable, or malformed selected file. Do not infer these rules from existing resolver behavior or use a conventional path as a default.

### SQL Server TLS

- **Approved mandatory policy:** require encrypted transport and validate both the server certificate and server identity. Invalid, untrusted, expired, or hostname/identity-mismatched certificates must fail closed.
- **Explicitly not approved:** `trustServerCertificate=true`, disabled encryption, reliance on JDBC driver-default fallback, or any environment-specific validation/encryption bypass.
- **Implementation and test details, not Owner policy choices:** specify the JDBC options, trust-anchor provisioning, and managed certificate/hostname implementation, then test them to demonstrate they satisfy the approved policy. These details must not weaken or bypass the requirements above.

## Acceptance evidence after approval

Run only in an authorized isolated environment with synthetic values and no production connection. First implement the approved contract separately; this proposal itself does not request or perform these changes.

1. **Packaged artifact and source resolution:** Build the shaded JAR and inspect its entries to verify `db.properties` is absent. Use no-network tests with synthetic values to verify support for both required source classes: process environment/secret injection and an external properties file loaded through its subsequently specified explicit path/interface. After path/interface and precedence are specified, assert the documented path and conflict rules, and prove that adjacent-JAR/current-working-directory files are not implicitly selected.
2. **Secret redaction:** Use distinct synthetic markers for password and full connection string. Assert none occur in resolver/target string representations, validation errors, thrown exceptions, stdout/stderr, or captured application diagnostics. Assert logs identify neither secret source contents nor full JDBC URL if it embeds credentials.
3. **Selected-file failures:** Once the remaining file failure semantics are specified, use synthetic missing, unreadable, and malformed-file cases to assert the specified behavior before any fake connection handoff and verify no synthetic secret markers leak. Do not infer fail-versus-ignore behavior before it is decided, and do not attempt a real connection.
4. **TLS configuration boundary:** Assert that the selected synthetic JDBC configuration enforces encryption and certificate plus identity validation, with no driver-default fallback, `trustServerCertificate=true`, or other bypass inserted. Verify consistent enforcement across the supported source combinations once their precedence is specified.
5. **Controlled TLS handshake:** Only after separate authorization, use a named synthetic SQL Server endpoint and the pinned JDBC driver/runtime. Record outcomes without credentials: a valid trusted certificate with matching identity succeeds; untrusted, expired, invalid, and hostname/identity-mismatched certificates fail closed. Include encryption negotiation evidence. Never treat a bypassed validation or successful connection using `trustServerCertificate=true` as acceptable evidence.
