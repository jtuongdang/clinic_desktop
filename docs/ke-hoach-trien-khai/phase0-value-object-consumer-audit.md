## Findings

### 1. `NgayKhoang`

**Fact — Domain contract and behavior.** `NgayKhoang` is a `LocalDate` pair: start is mandatory, end may be null; the constructor rejects end-before-start. `contains` includes both endpoints and treats null end as open-ended; `overlaps` treats a shared boundary as overlap (`clinic-domain/src/main/java/vn/clinicmanagement/domain/common/valueobjects/NgayKhoang.java:7-30`). Existing tests prove those behaviors, including null start, open-ended range, inclusive endpoints, and touching ranges (`clinic-domain/src/test/java/vn/clinicmanagement/domain/common/valueobjects/NgayKhoangTest.java:11-72`). They prove the class contract only, not a business policy for any model.

**Fact — Candidate model fields and actual flow.**

- `BaoHiem.ngayBatDau` / `ngayHetHan` are the closest live date-range candidate (`clinic-domain/src/main/java/vn/clinicmanagement/domain/patient/BaoHiem.java:11-12`). `RegisterBenhNhanHandler` requires an expiry when an insurance card number is supplied, permits a null start, and rejects start-after-expiry (`clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterBenhNhanHandler.java:181-200`). The schema likewise makes `ngayBatDau DATE NULL` and `ngayHetHan DATE NOT NULL` (`clinic-infrastructure/src/main/resources/migrations/V1__Initial_Clinic_Schema.sql:252-253`).
- The existing slice maps those dates as plain `LocalDate`: the form parses/formats the start and expiry, allowing blank optional dates (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/components/BenhNhanDangKyBieuMauManHinh.java:406-407,432-433,482-502`); `BaoHiemRepository` reads them from `ResultSet` and binds them as JDBC objects (`clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/BaoHiemRepository.java:24-25,56-79,127-128,148-170`).
- Other date-only pairs exist in `KyLuong` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/payroll/KyLuong.java:11-12`), `KyChamCong` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/identity/KyChamCong.java:7-8`), and `NghiPhep` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/identity/NghiPhep.java:10-11`). The checked-in source review found no corresponding Application consumer or Infrastructure adapter for these models; they are future candidates, not current consumers.
- `LichHen` has `LocalDateTime` start/end fields, not `LocalDate` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/appointment/LichHen.java:18-19`), so it is not a direct fit for this `NgayKhoang`. Reception queue queries currently take one `LocalDate`, not a range (`clinic-application/src/main/java/vn/clinicmanagement/application/reception/GetTiepDonHangDoiQuery.java:7-14`).

**Gap inventory.** No production code constructs or consumes `NgayKhoang`; no Application DTO/query carries it; no JDBC converter serializes or hydrates it; no desktop form or filter uses it; no non-Domain test checks model, use-case, persistence, or UI integration. The insurance slice has plain-date Application validation, JDBC mapping, and form coverage, but those tests do not establish `NgayKhoang` mapping (`RegisterBenhNhanHandlerTest.java`, `BenhNhanDangKyBieuMauManHinhTest.java`; relevant synthetic date round-trip assertions include `clinic-desktop/src/test/java/vn/clinicmanagement/desktop/modules/reception/components/BenhNhanDangKyBieuMauManHinhTest.java:301-302,382-383,469-470`).

**Recommendation — safe candidate and future files.** If the Owner approves the period semantics and null contract, start with the live `BaoHiem` start/expiry pair; keep `ngayMienCungChiTra` and `ngayDu5NamLienTuc` as separate optional milestone dates, not range endpoints. The implementation path would touch `clinic-domain/src/main/java/vn/clinicmanagement/domain/patient/BaoHiem.java`, `clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterBenhNhanHandler.java`, `clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/BaoHiemRepository.java`, and `clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/components/BenhNhanDangKyBieuMauManHinh.java`; add focused coverage to `clinic-domain/src/test/java/vn/clinicmanagement/domain/common/valueobjects/NgayKhoangTest.java`, `clinic-application/src/test/java/vn/clinicmanagement/application/reception/RegisterBenhNhanHandlerTest.java`, and `clinic-desktop/src/test/java/vn/clinicmanagement/desktop/modules/reception/components/BenhNhanDangKyBieuMauManHinhTest.java`, plus a new `clinic-infrastructure/src/test/java/vn/clinicmanagement/infrastructure/persistence/patient/BaoHiemRepositoryTest.java` (no dedicated insurance repository test was found in the reviewed test sources). Do not pass an optional null `ngayBatDau` to the current constructor. `KyLuong`, `KyChamCong`, and `NghiPhep` can be reconsidered with their respective approved use cases and mappings. Do not substitute `NgayKhoang` for `LichHen`’s timestamp interval.

### 2. `Tien`

**Fact — Domain contract and behavior.** `Tien` stores a `BigDecimal` plus currency, defaults null currency to VND, applies scale 2 with `HALF_UP`, and checks currency on arithmetic/comparison (`clinic-domain/src/main/java/vn/clinicmanagement/domain/common/valueobjects/Tien.java:8-58`). Tests cover default VND, half-up rounding, arithmetic, currency mismatch, null inputs, and equality (`clinic-domain/src/test/java/vn/clinicmanagement/domain/common/valueobjects/TienTest.java:13-79`). These are current implementation choices, not approved pricing/accounting policy. `DOMAIN_ANALYSIS.md:110` describes the same default/scale/rounding behavior but does not establish approval.

**Fact — Monetary model inventory.** The current Domain stores monetary-looking fields as `BigDecimal`, including:

**Gap inventory.** No model field, command/query, handler, JDBC mapper, or UI view model uses `Tien`; no infrastructure serialization/rehydration or currency round-trip test exists; the only `Tien` tests are its own Domain tests. UI monetary display is not connected to persisted invoice data. The only current invoice port is `IHoaDonRepository`; no service-catalog or order repository port was found (`clinic-domain/src/main/java/vn/clinicmanagement/domain/repositories/IHoaDonRepository.java:5-8`). Define or approve required ports before wiring new adapters. Future work would change those model files and introduce an agreed Application boundary such as `clinic-application/src/main/java/vn/clinicmanagement/application/billing/CreateHoaDonHandler.java` (new; name/path proposal), plus Infrastructure mappers such as `clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/billing/DanhMucDichVuRepository.java`, `clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/billing/ChiDinhDichVuRepository.java`, and `clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/billing/HoaDonRepository.java` (new). `clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/billing/VienPhiHoaDonManHinh.java` would then render the returned monetary values rather than its current sample strings. Keep non-monetary `BigDecimal` values outside this conversion; do not change schema based on this audit.

### 3. `DienThoaiSo`

**Fact — Domain contract and behavior.** `DienThoaiSo` rejects null/blank input, strips whitespace, dots, and hyphens, and accepts only the regex `0` or `+84` followed by supported Vietnamese mobile prefixes `3/5/7/8/9` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/common/valueobjects/DienThoaiSo.java:7-15`). It does not convert `0...` into `+84...` or vice versa. Tests cover both forms, separators, invalid prefixes/lengths, and blank input (`clinic-domain/src/test/java/vn/clinicmanagement/domain/common/valueobjects/DienThoaiSoTest.java:8-44`). `DOMAIN_ANALYSIS.md:111` describes a 10-digit pattern but omits the implemented `+84` form. These are current code/document behaviors, not an Owner-approved policy for every phone field.

**Fact — Candidate model fields and actual flow.** String phone fields appear in `BenhNhan.dienThoai` and `nguoiLienHeDienThoai` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/patient/BenhNhan.java:20,25`), `CoSo.dienThoai` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/facility/CoSo.java:11`), `NhanVien.soDienThoai` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/identity/NhanVien.java:13`), and `NhaCungCap.soDienThoai` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/inventory/NhaCungCap.java:8`). Only the patient contact fields currently participate in the inspected live reception flow:

- `BenhNhanDangKyBieuMauManHinh` accepts raw phone text, trims the primary number, maps an empty contact number to null, and re-renders model strings (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/components/BenhNhanDangKyBieuMauManHinh.java:320,329,361,377`). `RegisterBenhNhanHandler.validate` checks patient name/date/gender/room/insurance but has no phone validation (`clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterBenhNhanHandler.java:181-200`).
- `BenhNhanRepository` reads/writes phone columns as strings; it blanks the main phone to SQL null on write, writes the emergency contact directly, and searches the stored phone string (`clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/BenhNhanRepository.java:33-35,92,98-101,161-165,183-185,258,274,291,307,315,320`). The schema uses `VARCHAR(20)` for patient phone columns (`clinic-infrastructure/src/main/resources/migrations/V1__Initial_Clinic_Schema.sql:197,213`).
- Search results and a printed follow-up slip display the raw patient number (`clinic-application/src/main/java/vn/clinicmanagement/application/reception/BenhNhanSearchMatHang.java:5-9`; `clinic-desktop/src/main/java/vn/clinicmanagement/desktop/core/docx/DOCXExportDichVu.java:168`).
- `BenhNhanRepositoryTest` covers string/JDBC mapping with synthetic test values, not `DienThoaiSo` construction or canonicalized search (`clinic-infrastructure/src/test/java/vn/clinicmanagement/infrastructure/persistence/patient/BenhNhanRepositoryTest.java:234,260-322`). `RegisterBenhNhanHandlerTest` and `BenhNhanDangKyBieuMauManHinhTest` cover registration/form behavior but do not reference the VO; the latter's tests include ordinary date round trips (`clinic-desktop/src/test/java/vn/clinicmanagement/desktop/modules/reception/components/BenhNhanDangKyBieuMauManHinhTest.java:111-121,187`).

**Gap inventory.** No production consumer exists for any phone field. The checked-in Application boundary accepts raw strings without phone validation; JDBC mapping, indexed lookup, search, result display, and print output do not normalize through the VO. The Domain VO tests are the only direct tests of it; no application rejection/persistence/search/UI acceptance test verifies the integration. `CoSo`, `NhanVien`, and `NhaCungCap` fields are additional model candidates but no corresponding phone integration was found in this review.

**Recommendation — safe candidate and future files.** Start, if approved, with the live `BenhNhan.dienThoai` path and explicitly decide whether the optional emergency contact is in scope. Candidate files are `clinic-domain/src/main/java/vn/clinicmanagement/domain/patient/BenhNhan.java`, `clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterBenhNhanHandler.java` (or its command validation boundary), `clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/BenhNhanRepository.java`, `clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/components/BenhNhanDangKyBieuMauManHinh.java`, `clinic-application/src/main/java/vn/clinicmanagement/application/reception/BenhNhanSearchMatHang.java`, and `clinic-desktop/src/main/java/vn/clinicmanagement/desktop/core/docx/DOCXExportDichVu.java`. Retain a string representation at the JDBC boundary unless a separate schema migration is approved; ensure database lookup/search use the same agreed representation as writes. Add/extend synthetic tests in `clinic-domain/src/test/java/vn/clinicmanagement/domain/common/valueobjects/DienThoaiSoTest.java`, `clinic-application/src/test/java/vn/clinicmanagement/application/reception/RegisterBenhNhanHandlerTest.java`, `clinic-infrastructure/src/test/java/vn/clinicmanagement/infrastructure/persistence/patient/BenhNhanRepositoryTest.java`, and `clinic-desktop/src/test/java/vn/clinicmanagement/desktop/modules/reception/components/BenhNhanDangKyBieuMauManHinhTest.java`, including persistence read-back and search with equivalent entered formatting. Do not extend the mobile-only rule to employee, facility, or supplier numbers without confirming those data requirements.

## Owner decisions (policy blockers; no decisions made here)

1. **Phone format and optionality:** approve whether the domain accepts mobile-only Vietnam numbers, landlines, or international numbers; which prefixes and separators are accepted; whether storage/search canonicalizes `0...` and `+84...`; and whether the primary patient number and emergency-contact number may be blank/null. The current VO's nonblank/mobile-only behavior conflicts with the current patient registration path, which does not require or validate the primary phone; the emergency contact is optional.
2. **Date interval rules:** approve inclusive/exclusive boundaries for insurance validity, leave, and payroll periods. `NgayKhoang` currently treats both endpoints as inclusive and touching intervals as overlapping, but this is only code/test behavior. Decide whether start/end may be null per model. The live insurance start is optional while the VO start is mandatory; the current schema requires insurance expiry, and the handler requires it when a card number is supplied. Open-ended `NgayKhoang` end behavior therefore cannot be assumed to match stored insurance behavior.
3. **Currency and rounding:** approve supported currencies (VND-only or multi-currency), scale/rounding mode, and when rounding occurs (unit, line, discount/benefit split, invoice/payment total). The VO currently defaults to VND and rounds every construction to two decimals using `HALF_UP`; tests also exercise USD/EUR. Existing schema uses two-decimal monetary columns in relevant tables but does not establish calculation policy.
4. **Field scope:** approve whether Money is for service/insurance prices, invoice/receipt/debt balances, deposits, inventory prices, payroll, and/or other monetary values. Do not convert quantities, measurements, coefficients, or percentage rates.
