### 1. Approved queue persistence design basis: P1 + M3

Owner approved only the following **P1** and **M3** concepts as the architecture design basis. Earlier wording that included physical SQL details within the approval bullets is superseded by this clarification; the technical analysis is retained below as illustrative proposals requiring design review.

1. **P1 approved as persistence design basis:** Current `queueDate` and a pointer to the current allocation on `LuotKham`, with an immutable allocation ledger. No physical pointer name, type, nullability, FK/check or index is selected.
   - **Proposal rationale, not additional approval:** Inline current queue data could support frequent desktop UI reads ([`ReceptionQueueRepositoryImpl.getQueueList`][queue-reads] and [`GetDoctorQueueHandler`][doctor-date]) without requiring mandatory multi-table joins on every refresh.
2. **M3 approved as allocator design basis:** A transactional per `(roomId, queueDate)` high-water counter plus immutable `QueueAllocation` ledger. The tuple describes the logical sequence namespace, not approved SQL key syntax.
   - **Binding policy:** Allocations must be unique within the shared room/day sequence and committed numbers must never be reused. Exact database enforcement remains open. Counter field meanings, initialization/increment/rollback semantics, locking and SQL statements require further design review.
3. **Settled RECON-05 policies implemented without modification:**
   - **Shared room/day sequence:** Registration and transfer share exactly one number sequence per `(roomId, queueDate)`. No partitioning by priority, status, or role.
   - **No reuse of committed numbers & visible gaps allowed:** Committed sequence numbers are **never reused** within a room/day, even if a visit is subsequently transferred out, cancelled, completed, or soft-deleted. A visit returning A → B → A consumes a fresh allocation in A. Visible gaps in the queue sequence are explicitly permitted. Numbers in confirmed rolled-back transactions were never committed and may be allocated by subsequent attempts; no uncommitted number may be exposed via receipt, printing, or event.
   - **Single DB UTC clock authority:** Exactly one SQL Server DB UTC instant captured on the transaction connection at transaction start (before acquiring destination queue locks) determines the `Asia/Ho_Chi_Minh` queue date throughout the attempt, even if lock wait crosses clinic-local midnight.
   - **Atomic mutation, allocation, history, and audit:** Transfer visit projection update, destination queue allocation, immutable transfer history (`LichSuDieuChuyenLuotKham`), and security audit (`NhatKyHeThong`, action `VISIT_TRANSFERRED`) must commit atomically or roll back atomically in the same database transaction.
4. **Preserved high-water cutover safeguard (fail closed on unknown history):**
   - Migration design must establish the committed high-water mark from all trustworthy persisted allocation evidence, including soft-deleted rows/assignments and any retained historical assignment record.
   - If hard deletion, purging, overwritten assignments, or missing historical commits make the high-water unprovable, **cutover and both issuers must stop for the affected room/day** until a verifiable reconciliation source or a separately approved safe boundary exists. Legacy unknowns fail closed; do not infer, estimate, or fabricate history.

### 1. Binding facts and settled policies under RECON-05

The following decisions are approved and binding; they must not be treated as open options:

1. **Queue allocation policy and date separation:** `queueDate` is strictly separate from clinical `ngayKham`. Destination queue allocation derives its date from transfer execution and never mutates clinical `ngayKham`. Visit status, clinical `ngayKham`, reception time, and existing examination timestamps (`thoiGianBatDauKham`, `thoiGianKetThucKham`) remain preserved and intact. Priority (`dnVnTien`) is preserved unchanged without auto-promotion.
2. **Shared room/day sequence namespace:** Exactly one number stream per `(roomId, queueDate)` is shared by patient registration and visit transfer. Registration and transfer allocate from the same sequence. No partition by priority, status, or issuer role is permitted.
3. **No-reuse of committed numbers and gap allowance:** Committed sequence numbers are **never reused** within a room/day, even if a visit is subsequently transferred out, cancelled, completed, or soft-deleted. A visit returning A → B → A consumes a fresh allocation in A. Visible gaps in the queue sequence are explicitly allowed. Numbers in confirmed rolled-back transactions were never committed and may be allocated by subsequent attempts; no uncommitted number may be exposed via receipt, printing, or event.
4. **Transaction clock authority and midnight sampling:** Exactly **one SQL Server DB UTC instant** is captured on the transaction connection at transaction start (before acquiring destination queue locks) and converted to a clinic-local calendar date using `Asia/Ho_Chi_Minh` for `queueDate`. That single derived date governs the entire transaction attempt, even if lock contention or transaction execution crosses clinic-local midnight. Technical/audit metadata remains UTC.
5. **Atomic transfer mutation, allocation, history, and security audit:** A dedicated immutable transfer-history record (`LichSuDieuChuyenLuotKham`) and a successful security audit event (`NhatKyHeThong`, action `VISIT_TRANSFERRED`) are mandatory in the **same database transaction** as the visit mutation and queue allocation. All required writes commit together or roll back together. Audit-only logging is no longer permitted.
6. **Transfer reason taxonomy:** Exactly one of the six approved role-partitioned business reason codes is mandatory (`RECEPTION_TRIAGE_CORRECTION` for RECEPTIONIST only; `PATIENT_SPECIALTY_PREFERENCE` and `CLINIC_LOAD_BALANCING` for RECEPTIONIST or DOCTOR within scope; `CLINICAL_SPECIALTY_REFERRAL`, `DIAGNOSTIC_EQUIPMENT_NEED`, `CLINICIAN_EMERGENCY_HANDOFF` for DOCTOR only). The transfer reason is a business field and must never be placed into auth/authorization `AuditReasonCode` or `NhatKyHeThong.maLyDo`.
7. **Idempotency outcomes:** Same request key + same canonical payload after commit returns the stored operation receipt after reauthorizing the actor, without repeating allocation, mutation, history, or success audit. Same key + different payload returns a conflict without writes. On timeout or lost connection, retry with the same key and determine whether the transaction committed or rolled back before proceeding; timeout alone never proves rollback.

### 2. Concrete recommended persistence, allocator, transaction, and cutover design

The following analysis is retained as an **illustrative technical proposal requiring design review**, not an Owner-approved physical design. In particular, `maCapSoHienTai`, `queueDate DATE NULL`, `BIGINT`, `QueueDayCounter`, `UNIQUE (maPhongKham, queueDate, soThuTu)`, FKs/checks, index compositions, `UPDLOCK, HOLDLOCK`, and exact counter initialization/increment/return/rollback semantics are unapproved examples. The P1/M3 conceptual direction and binding policies above control; none of the SQL or operational steps below authorizes DDL, migration or runtime work.

#### 2.1. P1 conceptual basis — illustrative physical persistence proposal

- **Approval status:** Owner-approved architecture design basis under RECON-06 (`VIS-TRANSFER-OWNER-DECISION-RECON-06`). Physical DDL, schema column data types, constraints, indexes, and migrations remain unapproved and strictly open.
- **Illustrative physical design, not approved:** Store current `queueDate DATE NULL` directly on `LuotKham` alongside current `maPhongKham`, `soThuTu`, and `soThuTuDisplay`, accompanied by `maCapSoHienTai BIGINT NULL` referencing an immutable `QueueAllocation` record.
- **Rationale:** Desktop queue readers ([`ReceptionQueueRepositoryImpl.getQueueList`][queue-reads] and [`GetDoctorQueueHandler`][doctor-date]) query active room queues with high frequency. Storing `queueDate` inline allows immediate indexing on `(queueDate, maPhongKham, trangThai)` without introducing mandatory multi-table joins on every queue refresh.
- **Proposed integrity enforcement, not approved FKs/checks:** The current visit fields (`maPhongKham`, `queueDate`, `soThuTu`, `soThuTuDisplay`) are a synchronized projection of the authoritative `QueueAllocation` ledger. Both must be updated atomically in the same transaction, protected by database foreign key and transactional checks ensuring the allocation belongs to the visit.
- **Alternatives analyzed:**
  * *P2 (One current queue-assignment side table — NOT SELECTED / Historical alternative):* Cleanly isolates queue fields from clinical `LuotKham`, but requires an additional join on all desktop queue screens and complicates existing queries. Preserved as a historical analysis snapshot.
  * *P3 (Retained allocations with pointer only — NOT SELECTED / Historical alternative):* Stores `queueDate` exclusively in `QueueAllocation` with only an FK on `LuotKham`. Avoids duplicate date storage, but makes every queue reader join `QueueAllocation`, impacting query performance. Preserved as a historical analysis snapshot.
  * *P4 (Deriving date from history/audit — REJECTED / Historical alternative):* Fragile, unindexable, requires scanning history for current state; rejected as unsuitable for high-frequency desktop UI. Preserved as a historical analysis snapshot.

#### 2.2. M3 conceptual basis — illustrative physical allocator proposal

- **Approval status:** Owner-approved architecture design basis under RECON-06 (`VIS-TRANSFER-OWNER-DECISION-RECON-06`). Physical DDL, locking configuration, counter initialization SQL, and migrations remain unapproved and strictly open.
- **Illustrative physical design, not approved:** Propose a mutable coordination table `QueueDayCounter` paired with an immutable ledger table `QueueAllocation`.
  * `QueueDayCounter`: PK `(maPhongKham INT, queueDate DATE)`, `lastNumber INT NOT NULL`, `version BIGINT NOT NULL`, `updatedAt DATETIME2 NOT NULL`. Tracks the durable high-water mark for each room/day stream.
  * `QueueAllocation`: PK `id BIGINT IDENTITY`, `maLuotKham INT NOT NULL`, `maPhongKham INT NOT NULL`, `queueDate DATE NOT NULL`, `soThuTu INT NOT NULL`, `soThuTuDisplay VARCHAR(10) NOT NULL`, `loaiPhanBo VARCHAR(20) NOT NULL` (`TIEP_NHAN` or `DIEU_CHUYEN`), `maThaoTac NVARCHAR(100) NOT NULL`, `thoiGianCapUTC DATETIME2 NOT NULL`.
  * Proposed unique constraint syntax (not approved): `UNIQUE (maPhongKham, queueDate, soThuTu)` across all issued allocations. Uniqueness is required policy; this database enforcement choice still requires review.
- **Illustrative allocation sequence — exact counter semantics and SQL require review:**
  1. On the active transaction connection, query `QueueDayCounter` with `SELECT lastNumber FROM QueueDayCounter WITH (UPDLOCK, HOLDLOCK) WHERE maPhongKham = @targetRoom AND queueDate = @queueDate`.
  2. If missing, require the verified cutover baseline in Section 2.5; absence of a counter is not proof of first issuance. Insert `lastNumber = 0` with range protection only for a provably unused room/day; otherwise initialize from its verified high-water mark/safe boundary or fail closed.
  3. Atomically increment: `UPDATE QueueDayCounter SET lastNumber = lastNumber + 1, updatedAt = @nowUtc OUTPUT INSERTED.lastNumber WHERE maPhongKham = @targetRoom AND queueDate = @queueDate`.
  4. Format display string (minimum 2 digits, e.g. `%02d`, preserving larger numbers like `100` without truncation).
  5. Insert the immutable row into `QueueAllocation`.
- **Alternatives analyzed:**
  * *M1 (Current MAX over LuotKham — REJECTED):* Rejected by RECON-05/RECON-06. Moving or deleting visits lowers the maximum and reuses numbers, violating the binding no-reuse invariant.
  * *M2 (MAX over QueueAllocation ledger — NOT SELECTED / Historical alternative):* Feasible, but scanning/locking the ledger index under high concurrency creates range locks and potential lock escalation. Preserved as a historical analysis snapshot.
  * *M4 (SQL Server native SEQUENCE — NOT SELECTED / Historical alternative):* SQL Server sequences cannot be dynamically keyed by `(roomId, queueDate)` without dynamic DDL per room/day or cyclical resets; sequence rollbacks discard numbers unpredictably. Preserved as a historical analysis snapshot.

#### 2.3. Concurrency, locking, and atomic execution order

The illustrative sequence below proposes a deterministic resource order for review against concurrent bidirectional transfers A → B and B → A and shared registration/transfer allocation. It is not an approved lock hierarchy or a demonstrated deadlock-prevention guarantee; exact hints and cross-writer coordination remain open:

1. **Replay key check:** Check the idempotency request key with `UPDLOCK, HOLDLOCK`. If already committed, return the stored receipt.
2. **Visit CAS and row lock:** Execute conditional CAS update on `LuotKham` matching ID, `expectedVersion`, source facility, source department, null-safe source room, and eligible status. This locks the visit row and increments `version = version + 1`. If 0 rows are affected, abort immediately with a concurrency conflict.
3. **Target hierarchy verification:** Verify destination room, department, and facility are active and non-deleted via join on `PhongKham`, `Khoa`, `CoSo`.
4. **Counter acquisition:** Acquire `UPDLOCK, HOLDLOCK` on `QueueDayCounter` for `(destinationRoomId, queueDate)`.
5. **Allocation insert:** Insert new `QueueAllocation` record.
6. **Visit projection update:** Update `LuotKham` destination room, department, `queueDate`, `soThuTu`, `soThuTuDisplay`, `maCapSoHienTai`, and UTC timestamp.
7. **Transfer history insert:** Insert immutable record into `LichSuDieuChuyenLuotKham`.
8. **Security audit insert:** Insert `NhatKyHeThong` row with action `VISIT_TRANSFERRED`, correlation UUID, and actor context via `appendInCurrentTransaction`.
9. **Outermost commit:** The transaction commits all changes atomically. Only after outermost commit succeeds is the operation receipt exposed to the client.

#### 2.4. Rollback and failure recovery strategy
- **Statement/constraint failure:** If any statement fails (e.g. CAS version mismatch, unique constraint violation on `QueueAllocation`, target hierarchy inactive, or audit failure), `JdbcTransactionManager` issues `connection.rollback()`.
- **Complete undo:** Rollback restores visit fields, version, leaves no row in `QueueAllocation`, `LichSuDieuChuyenLuotKham`, or `NhatKyHeThong`, and rolls back the counter increment in `QueueDayCounter`. The unissued number is never exposed and remains available for subsequent transactions.
- **Indeterminate commit outcome:** If a network disconnect, client crash, or timeout occurs during commit, the client must treat the outcome as indeterminate. The client must retry using the **same request key**. The server checks the key; if committed, it returns the existing receipt; if absent and the previous transaction rolled back, it safely allows execution. Speculative compensating transfers are strictly prohibited.

#### 2.5. Migration, cutover sequence, and legacy data backfill
1. **Runner integration:** Migration must be written as a forward versioned script (e.g. `V12__Queue_Allocation_And_Transfer_History.sql`) and registered in [`DatabaseMigrationRunner.MIGRATION_SCRIPTS`][migration-runner].
2. **Preflight evidence and conflicts:** Inventory all trustworthy persisted allocation evidence: current and historical visits regardless of status or `isDeleted`, soft-deleted visits/allocations, retained allocation ledgers and any existing historical assignment record. Verify committed assignment identity, number, room and queue-day attribution; do not silently substitute clinical `ngayKham` or guess a legacy timezone. After correlating copies of the same proven assignment, group by `(roomId, queueDate, soThuTu)`: multiple distinct assignments sharing a tuple, conflicting copies, null/nonpositive numbers, unknown dates, orphaned rooms or corrupted versions block the affected room/day. Also reject multiple current assignments for a visit or disagreement between its current room/date/number and a retained current-assignment link. Do not merge, delete or renumber tickets to hide conflicts.
3. **Controlled writer barrier:** Pause all registration, transfer and direct/legacy allocation writers, or use an equivalent reviewed serialization barrier. Repeat preflight against the final stable snapshot before seeding and keep the barrier through synchronized cutover. Check the clinic-local current date from the single captured DB UTC instant; include any room/day that can receive allocations, not only active rooms. A day newly reachable after midnight needs its own verified baseline.
4. **Counter seeding (corrected):** For each `(roomId, queueDate)` stream to be enabled, establish `QueueDayCounter.lastNumber` at least as high as every trustworthy persisted committed assignment from step 2 and any verified retained high-water mark; never lower an existing counter. Use zero only when the absence of any prior committed allocation is verified for that room/day. Soft deletion, cancellation, completion or transfer out never removes evidence from this calculation. If hard-deleted records or commits without retained evidence may leave the committed-number high-water unproved, stop that room/day until a verifiable reconciliation source or owner-approved safe boundary is established as described in the corrective review. An empty result or observed MAX alone is insufficient; do not infer missing history or claim a no-reuse guarantee with incomplete evidence. Preserve legacy provenance without fabricating allocation/history rows.
5. **Synchronized allocator cutover:** Deploy the updated registration adapter ([`ReceptionQueueRepositoryImpl`][queue-register]) and the transfer handler simultaneously. Both must allocate numbers via the new `QueueDayCounter` + `QueueAllocation` mechanism.
6. **Queue query cutover:** Update queue queries ([`ReceptionQueueRepositoryImpl.getQueueList`][queue-reads] and [`GetDoctorQueueHandler`][doctor-date]) to query by `queueDate` (with fallback to `ngayKham` only for historical visits predating cutover).
7. **Legacy transfers:** When a legacy visit created before cutover is transferred for the first time, its source allocation link is stored as `NULL` and old queue number is preserved as informational data without fabricating historical allocation records.

### Current collision and locking analysis

1. **Normal registration path:** the handler encloses allocation and INSERT in one transaction, using the shared connection. The lock hints express an intention to protect the MAX read until the enclosing transaction completes. They are materially different from an unprotected `MAX+1`; current code must not simply be described as having no locking. Actual SQL Server locking, empty-range protection, escalation and contention remain to be exercised on an isolated test database.
2. **Standalone path:** the repository does not require an active transaction. Its [synthetic tests:112–168][queue-tests] explicitly exercise both transactional and standalone registration; standalone code never disables autocommit. With autocommit, allocator SELECT and INSERT are separate statement transactions: two callers can select the same next value before either inserts. The schema has no unique key to reject that collision. A UoW change count does not close this gap.
3. **Transfer-specific failure:** protecting the destination MAX does not protect an already issued number after the visit moves away. Example: room A/day D has only visit V at number 8; V transfers to B; A's current maximum can drop below 8. Later registration/return transfer can reissue historical numbers. Excluding deleted rows creates a similar hole. History without an allocation high-water mark does not repair this.
4. **Mixed writers:** a new transfer-only counter cannot coexist safely with unchanged registration MAX allocation. Once a visit leaves the target room, the old writer no longer sees its issued number. All issuers must share a protocol; uniqueness enforcement must also catch bypassing writers. A Java `synchronized` block cannot protect multiple desktop processes.
5. **Independent races:** a target number unique across visits does not prevent two moves of the same visit, and visit CAS does not make numbers unique across different visits. Both destination allocation serialization and visit CAS are required. Existing tests use synthetic scalar values; passing them would not prove SQL Server concurrent allocation safety.

This is not executable DDL or approved migrations. Physical schema/DDL, exact data types, table constraints, indexes, counter initialization, locking hints, and migration versions remain unapproved. No DDL is represented as approved or authorized for execution.

| Illustrative proposed record | Proposed data/enforcement requiring design review |
|---|---|
| `QueueDayCounter` | Primary key `(roomId, queueDate)`; nonnegative `lastNumber`. Room IDs are globally identified by the existing room PK; facility/department are validated ownership, not alternate sequence namespaces. `queueDate` is the separate queue date in `Asia/Ho_Chi_Minh`. Do not include priority/status in the key. Room reparenting must not create another sequence for the same room/day. |
| `QueueAllocation` | Allocation ID, visit ID, room ID, `queueDate` (transfer date in `Asia/Ho_Chi_Minh`, distinct from `ngayKham`), positive queue number, display snapshot, facility/department snapshots, operation kind (registration/transfer), operation ID and UTC issued time. | `LichSuDieuChuyenLuotKham` | Transfer/operation ID; visit ID; source and destination facility/department/room; old/new allocation references where known; old/new number/display; original clinical visit date (`ngayKham`, preserved) and destination queue date (`queueDate` in `Asia/Ho_Chi_Minh`); old/new visit version; preserved priority (`dnVnTien`); preserved visit status (`trangThai`); mandatory transfer reason code and optional short note (distinct from clinical reason fields; code taxonomy/length open); trusted employee/role/session/source-scope/workstation; correlation ID; UTC occurrence/creation time; local effective time/date and zone interpretation; request key/fingerprint and minimal committed receipt. |

**Illustrative enforcement proposal, not approved FKs/checks/DDL:** Use FKs to retained parent IDs without cascade deletion. Source room, old queue number/display and old allocation reference may be null for legacy visits: preserve that fact, never fabricate a former allocation or infer history from the current room. Destination room/date/number/allocation are mandatory. Verify source room hierarchy if populated; contradictory legacy ownership fails closed pending reconciliation. A missing source room alone does not reopen the approved mandatory **destination** room rule.

Enforce a unique transfer per `(visitId,newVersion)`, `newVersion=oldVersion+1`, equal old/new priority, positive target number, and consistent destination allocation ownership. Use constrained references/keys where expressible and transactional checks for the rest. The history record's own immutable state is distinct from the old/new **visit** versions. One transfer operation ID links ledger, history and receipt. An old allocation can be referenced as source by subsequent history without being updated or invalidated.

Make ledger/history append-only in the write API and database, following V6's UPDATE/DELETE rejection and immutable-state checks. Do not expose generic CRUD setters/soft-delete/restore. Corrections must append an independently authorized event; never rewrite a past source/target snapshot when room labels/ownership change. Parent-name joins cannot replace historical IDs/snapshots. Rollback of uncommitted INSERTs must remain possible; append-only means committed facts cannot be edited, not that aborted transactions retain rows.

The counter is intentionally mutable. It is infrastructure coordination state, not immutable clinical history. A unique ledger key is the final collision defense for participating allocation writers. It does not reject a writer that bypasses the ledger and directly updates `LuotKham`; neither does a counter alone. Before enablement, retire such writers and review database enforcement linking current visit assignments to their owned allocation, or equivalent restricted write access. Any current-visit unique constraint needs legacy review and cannot replace the ledger because a moved visit no longer holds its old room/date number. No gap-free or number-recycling policy is implied. Keeping issued numbers reserved is a recommendation requiring explicit queue-lifetime acceptance, consistent with the caution in [DEC-IDENTIFIER-01][time-policy]; that decision does not explicitly classify queue numbers.

## 4. Proposed atomic allocation and transfer protocol

The persistence adapter must reject use without an active transaction, following [ensureActiveLink:29–44][active-link] and current-transaction audit. Application owns authorization/use-case orchestration, Domain owns transfer invariants, and Infrastructure owns JDBC, allocation and constraints. Domain must not import SQL Server or Swing.

### Command/result boundary

Propose a transfer command carrying `visitId`, nonnegative `expectedVersion`, destination department/room IDs, stable client-generated operation key, mandatory fixed transfer reason code, and optional short note (distinct from clinical reason fields; code taxonomy/length open). Trusted session/audit context supplies actor, role, facility, source department, session, workstation and correlation. Neither queue number nor priority is client-editable. Do not accept an arbitrary client business date/backdate unless separately approved. A minimal receipt contains transfer ID, visit ID, destination IDs, separate `queueDate` in `Asia/Ho_Chi_Minh`, new number/display, new version and UTC occurrence time; visit status, clinical `ngayKham`, and examination timestamps are preserved; it contains no destination queue or patient details. These DTO fields and failure-code names require implementation-contract acceptance.

### One connection, one transaction

1. **Validate and authorize:** validate command/context consistency, active/unlocked/unexpired session, employee and assigned role/source pair using established fail-closed patterns. A transfer-specific guard implements the narrow same-facility exception; do not weaken [AuthorizationService:35–94][authorization], which correctly rejects ordinary target-pair mismatch. Source is the session's exact facility/department. RECEPTIONIST may choose a different target department only inside that facility; DOCTOR requires both departments equal the session selection. No patient detail/search/history or target queue calls are necessary.
2. **Resolve replay first:** inside the transaction serialize lookup of the operation key on its unique indexed key using the established `UPDLOCK,HOLDLOCK` shape. Validate persisted operation ownership/fingerprint before replaying. This precedes a current-source lookup: a successful prior transfer has already moved the visit out of its old source scope. Replay authorization must validate the original actor/source context, without granting current destination reads (details in section 6).
3. **Read and protect current facts:** lock the visit by ID and exact source scope, load version, source room/date/queue/priority/status/deletion/EMR state, and compare the supplied version. Resolve destination room joined through department and facility, require active/nondeleted hierarchy, and validate the approved role/scope relationship. Protect the hierarchy against deactivation/reparenting until commit with a reviewed locking strategy; a plain preflight read or an `EXISTS` check alone is not a demonstrated race barrier. Lock hierarchy rows in deterministic ID order where more than one is needed.
4. **Validate linked work:** obtain authoritative eligibility/handoff facts under the same consistency boundary. Preserve linked record attachment without mutation or billing changes, and ensure issued prescriptions, confirmed results, and posted financial records remain immutable, following the approved policy. Safe pending handoff requires verifying that the performing unit and responsibility remain intact. Because query readers and persistence adapters for linked work are not yet implemented in the codebase, the application cannot prove safe transfer or responsibility preservation; therefore, the adapter must fail closed, return failure, and allocate nothing. Do not infer safe emptiness from unloaded domain lists.
5. **Choose date/time once:** derive queue date (`queueDate`) from the transfer date in `Asia/Ho_Chi_Minh` as approved under `VIS-TRANSFER-OWNER-DECISION-RECON-04`, distinct from clinical `ngayKham`; capture a UTC operation timestamp. Store the chosen `queueDate` with the operation so a retry cannot silently switch days. Original clinical `ngayKham`, reception time, and existing examination timestamps (`thoiGianBatDauKham`, `thoiGianKetThucKham`) remain preserved and intact; do not silently mutate `ngayKham`.
6. **Allocate on the destination key:** within this same connection, select counter `(targetRoom,queueDate)` with `UPDLOCK,HOLDLOCK` on its unique key. For a missing key, protect the missing range before inserting initial state; a read-then-insert without range protection is insufficient. Atomically increment with `UPDATE ... OUTPUT INSERTED.lastNumber`, checking integer exhaustion before increment. Insert the new immutable ledger row with that value and locale-stable display compatible with current minimum two-digit formatting (`100` must not wrap to `00`). Concurrent issuers serialize on this key; different room/day keys may proceed independently, subject to SQL Server's actual lock plan/escalation. Registration and future appointment conversion must use this same allocator and ledger.
7. **CAS the visit:** update only department/room, number/display, the separate `queueDate` (or queue-link pointer) if persisted on visit, UTC updated metadata, and `version=version+1`. Predicate on visit ID, **expected source pair**, null-safe expected source room, supplied expected version, `isDeleted=0`, `emrLocked=0`, and the role's eligible persisted status set. Bind destination IDs proven by the protected hierarchy lookup. Preserve visit status (`CHO_KHAM`, `DANG_KHAM`, or `CHO_CLS`), original clinical `ngayKham`, examination timestamps (`thoiGianBatDauKham`, `thoiGianKetThucKham`), facility, priority, linked records and all clinical narrative fields; never auto-reset priority or clear doctor/start time as a side effect of allocation. A status/doctor/handoff transition belongs to the separately approved domain contract. Require exactly one affected row and capture persisted new version; zero means conflict/unavailable, never fallback INSERT or last-write-wins. Counter/ledger writes then roll back on failure.
8. **Append history and success audit:** persist the immutable before/after transfer facts (including mandatory fixed reason code and optional short note) and committed receipt, then append a proposed `VISIT_TRANSFERRED`/`VISIT`/visit-ID/`SUCCESS` system audit via `appendInCurrentTransaction`. Actor scope is the source session scope. Use the same correlation and occurrence time in history/audit; operation linkage is described below. Every required insert must affect exactly one row. No independently committed success audit and no best-effort history/audit.
9. **Commit before returning:** allow the boundary to commit only a successful result; expose the receipt only after the outermost commit succeeds. Refresh only authorized source reads through their existing authorization/audit handlers. Do not fetch target patient data or a target queue to prove success. Do not print/notify or dispatch irreversible side effects from inside the JDBC transaction.

This is a proposed transaction sequence, not current transfer SQL. The [existing indexed link protocol:14–18,29–44][active-link] and [history CAS][history-cas] are concrete precedents. The **new** counter/ledger/history keys, first-key creation and complete cross-writer lock ordering still need SQL Server acceptance.

### Contention and collision outcomes

| Race/failure | Required outcome of the proposed design |
|---|---|
| Different visits, same destination room/day, including first use of an empty day | Serialize on counter key/range; two distinct committed ledger numbers. Unique violation aborts the entire attempt; never proceed with a duplicated assignment. |
| Registration versus transfer, or transfer out and later back | Shared allocator/high-water mark and retained ledger prevent reissuing committed historical allocations. Release requires all issuers migrated together; old MAX writer coexistence is a blocker. |
| Two transfers of one source version to different rooms | Exactly one CAS wins; the loser has no committed number reservation, history or success audit. A row lock can serialize reads but does not replace expected-version checking. |
| Concurrent identical request key | Key/range serialization lets the loser observe and return the winner's stored receipt after commit; no second allocation, version bump, history or success audit. |
| Opposite transfers A→B and B→A, hierarchy edit, or another lifecycle writer | Deadlock/blocking is possible. Establish a shared order for operation key, visit, hierarchy/linked-work resources and destination counter; review all competing writers and actual plans. Avoid holding one room counter while acquiring another. On deadlock/lock timeout, abort and retry the whole transaction on a fresh connection with the same request key/version; never resume after a partially failed statement. |
| Number exhaustion or constraint/malformed ownership failure | Safe failure and complete rollback. Do not wrap, promote priority, renumber other visits or silently create a new sequence namespace. |

No guarantee of only row locks, zero deadlocks or independent-room throughput is made. `ROWLOCK` alone would not prove collision freedom. Retry count/backoff/timeout values remain implementation choices; do not turn a stale-version conflict into an automatic reload-and-reapply to a newly moved visit.

## 5. History and same-transaction audit linkage

Recommend structured transfer history plus a security audit, rather than storing the only transfer facts in free-text audit columns. Existing [system audit DTO][system-entry] cannot carry a before/after payload; the [writer][audit-writer] deliberately sets `chiTiet`/`lyDo` to null. The older memo's `AuditLog` JSON alternative is not an existing repository API.

A minimal proposed linkage uses a persisted **operation correlation UUID unique for each committed transfer**, stored with the operation key in history and in the success audit. Persist and reuse this correlation on replay; per-attempt diagnostic correlation may be separate. Enforce one success event per transfer operation/action with a narrowly reviewed constraint or explicit history↔audit-ID relationship. Current `AuditWritePort` returns void and existing audit correlation has no unique constraint, so neither database FK linkage nor exactly-once audit identity is already provided. The final choice between dedicated operation/audit IDs and correlation-based linkage needs a separate API/schema review; keep one unambiguous join and test it. Never make correlation globally unique across all existing audit actions: registration legitimately writes multiple actions with one correlation.

Full source/target IDs, old/new queue/date/version and unchanged priority live in the immutable history record. The system audit carries stable action/resource/actor/outcome/time and the join key. Do not put clinical narrative, patient names/contact/identifiers or unrestricted reason text into logs. ## 6. Optimistic conflict, replay and rollback semantics — proposed

Recommend durable replay from the immutable committed transfer record, not a process-local cache or the inventory model's default 24-hour expiry. A separate mutable in-progress receipt table is unnecessary if an indexed missing-key lock serializes requests and history/receipt appear only at commit. If later chosen, its lifecycle must be atomic too.

Proposed key namespace: `(operationType, actorEmployeeId, roleId, sourceFacilityId, sourceDepartmentId, clientRequestKey)`, unique independently of payload and session UUID. This permits recovery after process restart or a new valid session in the same role/scope. Record session UUID as evidence, not the only replay namespace. Validate key length/format and do not leak whether another actor's key exists. Key scope, lifetime and replay after permission revocation remain decisions for the final contract, not owner approvals here.

Canonical request equality covers visit ID, original expected version, target facility/department/room, trusted actor/role/source pair, and approved reason/effective-date inputs. Store a versioned canonical fingerprint with sufficient normalized fields to check equality; do not rely solely on JSON property order. Exclude per-attempt correlation/network timestamps and server-derived current date; compare against the original request, not the current visit state. Store the server-selected business date/receipt with the original operation. Reason normalization must follow its eventual contract.

| Condition | Proposed result and writes |
|---|---|
| New key, valid guards and expected version | Allocate/move once, increment version once, one history and one success audit, commit receipt atomically. |
| Committed key + equal payload + authorized original operation owner | Return the **original minimal receipt**, explicitly a replay. No allocation, mutation, version bump or second success audit, even if the visit has moved again. Never return current destination records. |
| Same key + different payload (including changed target, reason or expected version) | Reject key reuse with a stable non-sensitive conflict; no writes. A legitimate new transfer requires a new key and newly loaded authorized version. |
| No matching committed key + stale expected version | Return concurrency conflict/unavailable after authorization; no automatic rebasing. Do not reveal another department's new location/version to an unauthorized source actor. |
| Concurrent equal key while first transaction is unresolved | Wait within a bounded policy, then replay committed history or execute only if the first rolled back. Timeout returns retryable/unknown status; it does not authorize a second key. |
| Denied/revoked/invalid context or missing/ambiguous dependency | Fail closed; no receipt disclosure or new transfer. A key is not an authorization capability. Replay must revalidate identity/session/assignments and the accepted original-operation replay policy, rather than requiring a current destination read. |
| Audit/history/ledger/CAS failure before commit | Return failure and roll back counter initialization/increment, allocation INSERT, visit fields/version/metadata, history, receipt and success audit. No durable success key survives. Independent denial/failure audit, if specified, must truthfully describe failure and must not replace the required atomic success audit. |
| Commit acknowledgement lost, connection/rollback failure | Report an indeterminate safe failure; do not promise that data was never committed. Reconcile on a fresh connection through the same key. If committed, replay its receipt; if absent after the prior transaction is resolved, retry with the original version/key. No compensating move on speculation. |

The [transaction manager][transaction-manager] rolls back operation failures and failure results but maps SQL/commit errors to generic `TRANSACTION_FAILED`; its commit-error catch does not explicitly prove successful rollback. Therefore failure messaging and replay reconciliation must distinguish a known aborted attempt from unknown commit outcome. Rollback itself can fail. Do not copy registration's unconditional “data not saved” wording into an uncertain commit result.

Once committed, a “rollback” requested by an operator is a **new** authorized transfer with new number, key, version, history and audit, subject to eligibility/handoff/date rules; it is not deletion of history or decrementing a counter. This is a proposed correction approach, not a new undo permission. Client cancellation after submission likewise cannot imply database rollback after commit.
