## Conclusion and policy boundary

`DateRange` implements the approved conservative unknown-start semantics coherently, but its Boolean results must not be interpreted as coverage decisions. Reception permits absent phones, validates supplied phones with the existing rule, preserves prefixes, and keeps card registration separate from adjudication. The material implementation gap is that the cleaned phone value is discarded before storage. There is also a contained exception-message privacy risk and incomplete regression/consumer acceptance evidence, detailed below.

The controlling decisions are the explicit Owner statements in [owner decisions:24–26](phase0-value-object-owner-decisions.md#L24-L26), [39–41](phase0-value-object-owner-decisions.md#L39-L41), and [54–69](phase0-value-object-owner-decisions.md#L54-L69). The older UI guidance describes expiry warnings and a suggestion to change payer type ([UI_CODING_STANDARDS.md:511–516](../../UI_CODING_STANDARDS.md#L511-L516)); it does not supersede the approved non-blocking reception contract.

A bounded follow-up can document `contains` alongside the existing overlap Javadoc and add unknown-endpoint combination tests without changing the approved truth values or introducing a new coverage policy.

## BHYT registration is not adjudication

For a supplied card number, validation requires an expiry date, a recorded rate from 0 to 100 and non-inverted known dates. It does not compare card dates against today. BHYT payer without a number is rejected for missing registration data ([RegisterPatientHandler.java:197–210](../../clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterPatientHandler.java#L197-L210)). The recorded rate check is not a calculation or approval of payable benefits.

The handler adds/updates the card, then calls the queue with the requested payer type and returns an operational receipt ([RegisterPatientHandler.java:104–134](../../clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterPatientHandler.java#L104-L134)). **Source inference:** an otherwise valid expired card, future-start card, or unknown-start card does not by itself block registration or force a different payer. No date-based coverage service is invoked in this handler.

There is partial test-source support for unknown start: the successful BHYT registration test uses `validInsurance()`, which sets expiry and rate but never start ([RegisterPatientHandlerTest.java:123–176,610–615](../../clinic-application/src/test/java/vn/clinicmanagement/application/reception/RegisterPatientHandlerTest.java#L123-L176)). It verifies card and visit calls, but not a null-start JDBC read-back. There is no dedicated expired-card success, future-start success, same-day dates, handler inversion failure or expiry-day registration regression in the inspected handler tests. The domain inversion and endpoint tests cannot substitute for these handler checks.

Form conversion uses nullable date parsing ([PatientRegistrationFormPanel.java:401–407,488–492](../../clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/components/PatientRegistrationFormPanel.java#L401-L492)); JDBC binds the two dates and maps nullable SQL dates back ([BaoHiemRepositoryImpl.java:126–128,151–171](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/BaoHiemRepositoryImpl.java#L126-L171)). These are source observations only. They do not verify actual SQL Server null handling, schema constraints, form-to-handler behavior or coverage validity.

## Actionable findings and bounded follow-ups

### F1 — Medium: validated phone cleaning does not reach the stored value

The Owner requires separator-cleaned storage while preserving prefix ([owner decisions:39–41](phase0-value-object-owner-decisions.md#L39-L41)). The handler constructs and discards the VO ([RegisterPatientHandler.java:213–220](../../clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterPatientHandler.java#L213-L220)), then passes the original patient to persistence ([98–99](../../clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterPatientHandler.java#L98-L99)). The test explicitly expects spaces/hyphens to survive ([RegisterPatientHandlerTest.java:89–103](../../clinic-application/src/test/java/vn/clinicmanagement/application/reception/RegisterPatientHandlerTest.java#L89-L103)). Form conversion trims only outer whitespace ([PatientRegistrationFormPanel.java:361,377,505](../../clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/components/PatientRegistrationFormPanel.java#L361-L377)). JDBC binds primary with trim/blank-to-null and emergency as supplied on insert/update ([BenhNhanRepositoryImpl.java:286–331](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/BenhNhanRepositoryImpl.java#L286-L331)).

**Inference, not a database observation:** internally separated valid input can reach SQL unchanged, contrary to the approved cleaned-storage condition. Existing phone lookup uses trimmed equality and scoped search uses a literal escaped substring, without separator or prefix equivalence normalization ([BenhNhanRepositoryImpl.java:89–125](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/BenhNhanRepositoryImpl.java#L89-L125)); equivalent representations are not established by this code review.

**Proposed bounded fix in a separate implementation task:** retain the validated VO value for each supplied phone at the reception write boundary; preserve `0`/`+84` and absence, and do not backfill legacy rows. Update the focused test to assert cleaned values passed to the repository, then verify synthetic read-back and scoped search under a separately authorized acceptance task. Preserve existing scope constraints; this recommendation does not authorize a new search policy or schema/UI change.

### F2 — Medium, contained in reception: PhoneNumber embeds invalid input in its exception

[PhoneNumber.java:14](../../clinic-domain/src/main/java/vn/clinicmanagement/domain/common/valueobjects/PhoneNumber.java#L14) concatenates `rawPhone` into the invalid-format exception. A caller displaying or logging that message could expose the entered contents. This is direct source evidence of sensitive content in the exception, not evidence that a current reception message or log leaked it. Reception's local catch suppresses the exception ([RegisterPatientHandler.java:213–220](../../clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterPatientHandler.java#L213-L220)); the production-source search found this as the only VO construction consumer. `toString()` also returns the number ([PhoneNumber.java:31–32](../../clinic-domain/src/main/java/vn/clinicmanagement/domain/common/valueobjects/PhoneNumber.java#L31-L32)), so the object must not be logged as an ordinary diagnostic value.

Unexpected reception failures use fixed operation/result codes and bounded diagnostics ([RegisterPatientHandler.java:137–140](../../clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterPatientHandler.java#L137-L140)); the formatter records exception types/frames rather than messages ([ApplicationFailureDiagnostics.java:42–77](../../clinic-application/src/main/java/vn/clinicmanagement/application/common/ApplicationFailureDiagnostics.java#L42-L77)). Existing diagnostics tests assert omission of synthetic message/cause contents and guard against `getMessage()`/`toString()` access ([ApplicationFailureDiagnosticsTest.java:14–37,88–109](../../clinic-application/src/test/java/vn/clinicmanagement/application/common/ApplicationFailureDiagnosticsTest.java#L14-L109)); those tests were read, not executed here.

**Proposed bounded fix:** remove raw input from the VO exception message and add a synthetic exception-message privacy assertion to `PhoneNumberTest`, retaining reception's generic message. Do not change the accepted prefix set or optionality. Its current tests assert exception type only ([PhoneNumberTest.java:18–38](../../clinic-domain/src/test/java/vn/clinicmanagement/domain/common/valueobjects/PhoneNumberTest.java#L18-L38)).

### F3 — Medium: regression and consumer acceptance remain incomplete

The cited domain tests cover the main date truth table, but the inspected handler tests only partially protect the approved reception policy: the phone cases are at [RegisterPatientHandlerTest.java:75–121](../../clinic-application/src/test/java/vn/clinicmanagement/application/reception/RegisterPatientHandlerTest.java#L75-L121), and the default successful insurance fixture is at [610–615](../../clinic-application/src/test/java/vn/clinicmanagement/application/reception/RegisterPatientHandlerTest.java#L610-L615). The handler date branches at [RegisterPatientHandler.java:197–204](../../clinic-application/src/main/java/vn/clinicmanagement/application/reception/RegisterPatientHandler.java#L197-L204) lack the explicit cases identified above.

Read form-test excerpts establish mapping and blank emergency handling ([PatientRegistrationFormPanelTest.java:86–140](../../clinic-desktop/src/test/java/vn/clinicmanagement/desktop/modules/reception/components/PatientRegistrationFormPanelTest.java#L86-L140)); they convert to a command using synthetic strings, without invoking the handler. Known insurance dates are asserted in mapping at [469–470](../../clinic-desktop/src/test/java/vn/clinicmanagement/desktop/modules/reception/components/PatientRegistrationFormPanelTest.java#L469-L470). The existing SQL Server test is explicitly opt-in ([ReceptionSqlServerPersistenceTest.java:72–90](../../clinic-desktop/src/test/java/vn/clinicmanagement/desktop/modules/reception/ReceptionSqlServerPersistenceTest.java#L72-L90)), uses known starts and future expiries ([96–100](../../clinic-desktop/src/test/java/vn/clinicmanagement/desktop/modules/reception/ReceptionSqlServerPersistenceTest.java#L96-L100)), and has phone/date read-back assertions ([642–677](../../clinic-desktop/src/test/java/vn/clinicmanagement/desktop/modules/reception/ReceptionSqlServerPersistenceTest.java#L642-L677)). Its presence does not prove these new edge cases or a successful run.

**Proposed bounded fix:** add synthetic focused regressions for both phone absence permutations, cleaned repository inputs, private rejection messages, expired/future/unknown-start BHYT acceptance without payer reassignment, same-day dates and known inversion rejection before writes. Add date tests for both unknown starts and both null endpoints while retaining current semantics. Complete form → handler → JDBC → read-back and scoped-search acceptance only in a separately authorized synthetic integration task. Existing handler repositories/queue are proxies and the transaction probe stages in-memory strings ([RegisterPatientHandlerTest.java:707–787,825–848](../../clinic-application/src/test/java/vn/clinicmanagement/application/reception/RegisterPatientHandlerTest.java#L707-L848)); they do not verify JDBC transactions, SQL Server, actual persistence or visual Swing behavior. No tests were added here because the approved report-only scope forbids test edits.
