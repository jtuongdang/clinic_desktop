# Phase 1 — Doctor station history UI integration contract

**Historical status (reviewed 2026-11-06):** Source analysis only; no code, schema, permission, database, or UI change was authorized by this report at that time. This opening analysis is a historical snapshot, not the current implementation state; see the dated evidence addenda below.
**Reviewed date:** 2026-11-06
**Scope:** Wire the accepted patient-level `TienSuBenh` read/write application workflow into `BacSiTramManHinh`, alongside a safely identified doctor queue.
**Policy baseline:** `docs/ke-hoach-trien-khai/phase1-tiensuben-scope-contract.md` is owner-approved; it explicitly says UI wiring remains pending and current UI must not synthesize history (lines 1-5, 25-30).

## Historical finding — source state reviewed 2026-11-06

The existing history application layer is already scoped and audited, but the Doctor station is still a static prototype. `BacSiTramManHinh` constructs ten hard-coded `BenhNhanKhamDuLieu` rows, selects one by index, and has an empty `refreshData()`; the DTO carries display strings and no patient or visit identifier (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/doctor/BacSiTramManHinh.java:22-40,147-155`; `clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/doctor/model/BenhNhanKhamDuLieu.java:6-24,41-60`). `BacSiTienSuManHinh.updateHistory()` only resets a “no verified history” label (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/doctor/components/BacSiTienSuManHinh.java:13-39`). Therefore no selected row can safely supply `patientId` to `GetBenhNhanTienSuQuery`, `visitId` for encounter-bound actions, or trusted authorization/audit contexts. Parsing a displayed patient code, diagnosis, date, or department is not a substitute for persisted IDs or session context.

The application workflow is available: `GetBenhNhanTienSuHandler` rejects invalid/missing context, requires role code `DOCTOR`, requires matching authorization/audit actors, evaluates `PATIENT:XEM` against the session’s exact facility+department pair, queries by patient and both scope IDs, then appends independent `PATIENT_VIEW`/`PATIENT` audit with the requested patient ID before returning results (`clinic-application/src/main/java/vn/clinicmanagement/application/patienthistory/GetBenhNhanTienSuHandler.java:41-78,81-96`). The repository excludes deleted rows, null-scope legacy rows, and categories outside `BENH_NEN`, `DI_UNG`, and `PHAU_THUAT` while matching patient + facility + department (`clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/TienSuBenhRepository.java:17-25,33-50`). `SaveBenhNhanTienSuHandler` applies the same DOCTOR + `PATIENT:XEM` guard, verifies the patient in scope, derives new row ownership from the trusted session context, updates only an active exact-scope row/version, and writes `PATIENT_UPDATED`/`PATIENT` in the mutation transaction (`clinic-application/src/main/java/vn/clinicmanagement/application/patienthistory/SaveBenhNhanTienSuHandler.java:47-105,109-140`). These guards must remain the enforcement boundary.

## Current integration gaps and constraints

### Identity and session context

- The static sample rows in `BacSiTramManHinh.initPatientData()` contain no persisted IDs, and `BenhNhanKhamDuLieu` has no ID fields; its `getShortCode()` merely parses the human-readable code (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/doctor/BacSiTramManHinh.java:37-81`; `clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/doctor/model/BenhNhanKhamDuLieu.java:6-24,41-60`). The repository queue read model already returns both `visitId` and `patientId` (`clinic-application/src/main/java/vn/clinicmanagement/application/reception/TiepDonHangDoiMatHang.java:5-6`; `clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/reception/TiepDonHangDoiRepository.java:84-100`). Use those IDs directly in a queue view model; never derive them from names/codes or from a history row.
- The selected row is currently located through a table row index against the original list, so adding sorting/filtering or refreshing a queue can make the visible row and selected object diverge (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/doctor/components/BacSiHangDoiThanhBen.java:116-125`). Bind selection to the row’s immutable queue item/view model and retain both IDs.
- The current panel has a no-argument constructor and no session, use-case, or composition dependency. In contrast, `TiepDonManHinh` requires `PhienVongDoiDichVu` and its composition root constructs the application handlers/adapters (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/doctor/BacSiTramManHinh.java:30-35`; `clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/TiepDonManHinh.java:42-46`; `clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/TiepDonGhepNoiGoc.java:20-37`). `MainBangDieuKhienCuaSo` currently creates `new BacSiTramManHinh()` (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/dashboard/MainBangDieuKhienCuaSo.java:148-162`).
- `PhienVongDoiDichVu.currentAuthorizationContext()` and `currentAuditActorContext()` return operation contexts only while the lifecycle is active; the former binds employee, role, selected facility+department, and session UUID, and the latter creates per-operation audit correlation metadata (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/core/session/PhienVongDoiDichVu.java:307-328`). The authorization evaluator revalidates active/unlocked/unexpired session, current employee and role assignment, exact assigned work-scope pair, and a unique allowed `KHOA_PHONG` grant, denying on errors (`clinic-application/src/main/java/vn/clinicmanagement/application/authorization/PhanQuyenDichVu.java:20-32,34-115`). Do not construct contexts from a DTO or let a view model supply scope.

### Queue contract, gate, filters, and statuses

- The existing reception queue query is protected by module `RECEPTION`, action `XEM`; the handler audits a successful load as `PATIENT_VIEW`. Its query takes one date and both IDs from the authorization context (`clinic-application/src/main/java/vn/clinicmanagement/application/reception/GetTiepDonHangDoiHandler.java:32-54`). The existing grant seed includes `DOCTOR:RECEPTION:XEM` and `DOCTOR:PATIENT:XEM` (`clinic-infrastructure/src/main/resources/migrations/V8__Seed_Approved_Permission_Grants.sql:19-28`). Keep the queue’s `RECEPTION:XEM` gate distinct from the patient history’s `PATIENT:XEM` gate; passing one does not imply the other. No grant change is needed for this proposal.
- `TiepDonHangDoiRepository.scopedQueueSql()` constrains `ngayKham`, `maCoSo`, and `maKhoa`, excludes deleted visits/patients and `DA_HUY`, orders by priority, queue number and visit ID, but has no doctor-ID or room-ID predicate (`clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/reception/TiepDonHangDoiRepository.java:125-134`). It therefore returns the department’s queue for that date, across rooms, not a provider-assigned queue. `maBacSi` is nullable in `LuotKham` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/examination/LuotKham.java:29-43`); the reception registration insert does not set it (`clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/reception/TiepDonHangDoiRepository.java:33-58`). A provider filter cannot safely be presumed to work on current registrations.
- Current visit statuses are `CHO_KHAM`, `DANG_KHAM`, `DA_KHAM`, `KET_LUAN`, `HOAN_THANH`, `DA_HUY`, and `CHO_CLS` (`clinic-domain/src/main/java/vn/clinicmanagement/domain/common/enums/TrangThaiLuotKham.java:3-10`). The reception queue SQL excludes only `DA_HUY`, so same-day completed/closed statuses can also appear. The Doctor UI standard describes queue status filters for waiting, awaiting CLS results, and completed (`UI_CODING_STANDARDS.md:241-246`), but that is design guidance rather than an implemented selection rule. Its current sidebar date range and “all patients / all departments” footer are static labels, not working filters (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/doctor/components/BacSiHangDoiThanhBen.java:30-45,134-141`).
- Recommended safe starting point: reuse the existing scoped reception queue read with the current local `LocalDate`, show all rooms within the exact session department, and explicitly limit the Doctor view to the Owner-approved active statuses once confirmed. Do not expose the static “all departments” control, silently widen date/scope, or imply provider assignment. The minimal queue use case may return only queue items (rather than room summaries) while retaining `RECEPTION:XEM`, exact-pair SQL predicates, current session revalidation, and independent successful-read audit. If current behavior must remain byte-for-byte, a doctor-facing adapter can first consume `GetTiepDonHangDoiHandler` and map its queue; it must not bypass that handler’s guard.

### History category and read/write audit contract

- The accepted row scope contract limits history to exact `(facilityId, departmentId)` ownership, approved categories, verified rows, and no legacy inference; it requires `DOCTOR`, `PATIENT:XEM`, and successful-read audit `PATIENT_VIEW` + resource `PATIENT` + requested patient ID, with audit commit before response and fail-closed behavior (`docs/ke-hoach-trien-khai/phase1-tiensuben-scope-contract.md:7-14,22-30,42-45`). The JDBC read predicate enforces exact pair and excludes null ownership, soft-deleted rows, and unsupported categories (`clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/patient/TienSuBenhRepository.java:19-23,33-50`).
- A history-panel refresh for a selected patient is a separately audited patient read. The current history handler audits one successful patient-level read, including a successful empty result; repository failure writes no successful-read event, and audit failure returns a failure with no history value (`clinic-application/src/main/java/vn/clinicmanagement/application/patienthistory/GetBenhNhanTienSuHandler.java:58-78`; `clinic-application/src/test/java/vn/clinicmanagement/application/patienthistory/GetBenhNhanTienSuHandlerTest.java:32-68,131-155`). Do not treat the queue’s audit as authorization or audit coverage for a later history read.
- Queue reads use `PATIENT_VIEW` with null resource type and resource ID, which intentionally audits the queue operation without enumerating patient IDs (`clinic-application/src/main/java/vn/clinicmanagement/application/reception/TiepDonReadKiemToan.java:34-55`; `docs/ke-hoach-trien-khai/phase2-reception-read-authorization-contract.md:13-29`). History read must keep patient ID in `resourceId` as specified by the approved contract. `AUDIT_READ` is a separate denied capability (`clinic-application/src/main/java/vn/clinicmanagement/application/authorization/PhanQuyenDichVu.java:43-48`; `docs/ke-hoach-trien-khai/phase1-tiensuben-scope-contract.md:14`).
- The write handler accepts only `BENH_NEN`, `DI_UNG`, and `PHAU_THUAT`; creates rows using context scope; and updates via active row ID + patient ID + exact scope + optimistic version, auditing `PATIENT_UPDATED`/`PATIENT` with patient ID in the same transaction (`clinic-application/src/main/java/vn/clinicmanagement/application/patienthistory/SaveBenhNhanTienSuHandler.java:63-100,109-140`). It does not delete, and the scope contract excludes delete, other categories, and post-lock editing (`docs/ke-hoach-trien-khai/phase1-tiensuben-scope-contract.md:14`). The UI should call this handler for create/update rather than directly editing repositories or mutating a displayed entity.
- There is a policy-to-handler gap for lock state: `SaveBenhNhanTienSuCommand` contains patient/history IDs, version, category, narrative, and contexts but no visit ID (`clinic-application/src/main/java/vn/clinicmanagement/application/patienthistory/SaveBenhNhanTienSuCommand.java:8-16`); the handler verifies patient scope and exact history ownership but never loads a visit or checks `emrLocked` (`clinic-application/src/main/java/vn/clinicmanagement/application/patienthistory/SaveBenhNhanTienSuHandler.java:63-100`). `TienSuBenh` is patient-level and does not identify a locking visit; the review records encounter binding and post-lock semantics as unresolved (`clinic-domain/src/main/java/vn/clinicmanagement/domain/patient/TienSuBenh.java:5-19`; `docs/ke-hoach-trien-khai/phase1-tiensuben-review.md:39-48,55-58`). Do not claim the current write handler enforces the approved post-lock restriction; keep update/edit disabled until an unambiguous lock rule is agreed and enforced in Application.
- Keep the separate concepts separate: the approved panel workflow is `TienSuBenh` patient history, while the UI coding standard also describes prior encounter history and current-day CLS results (`UI_CODING_STANDARDS.md:266-269`). Do not populate either with the current encounter’s diagnosis or the static DTO. Encounter history and CLS require their own scoped, authorized, audited use cases before rendering.

## Minimal safe implementation contract

1. **Composition and trusted contexts.** Add a doctor composition boundary parallel to `TiepDonGhepNoiGoc`, constructing the existing history handlers, JDBC adapters, `PhanQuyenDichVu`, transaction boundary, and audit writer from shared desktop infrastructure (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/TiepDonGhepNoiGoc.java:20-37`). Inject the resulting services and `PhienVongDoiDichVu` into `BacSiTramManHinh`; update the dashboard construction site accordingly (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/dashboard/MainBangDieuKhienCuaSo.java:148-162`). Capture fresh `currentAuthorizationContext()` and `currentAuditActorContext()` for each queue/history operation. Missing either context, a non-DOCTOR role, inactive/locked/expired/revoked session, mismatched actor, wrong scope, missing/ambiguous/denied permission, query failure, or audit failure must render no protected history data. Application handlers remain authoritative even if the UI hides controls.
2. **Doctor queue.** Replace the hard-coded list and no-op `refreshData()` with an application-backed queue read. Carry stable `visitId` and `patientId` in its row model, and retain display fields separately (`clinic-application/src/main/java/vn/clinicmanagement/application/reception/TiepDonHangDoiMatHang.java:5-6`). Use exact context facility+department only. Keep the queue’s existing `RECEPTION:XEM` check and queue audit granularity; history must separately invoke `GetBenhNhanTienSuQuery` under `PATIENT:XEM`. Do not add or broaden permissions (`clinic-infrastructure/src/main/resources/migrations/V8__Seed_Approved_Permission_Grants.sql:19-28`; `docs/ke-hoach-trien-khai/phase2-reception-read-authorization-contract.md:13-19`).
3. **Selection-to-history.** On queue selection, synchronously clear prior history before starting a request, then call `GetBenhNhanTienSuHandler` with the selected item’s persisted `patientId` and fresh operation contexts. Render only the returned approved `TienSuBenh` rows. Empty success shows the existing empty-state message. On any failure, clear all prior rows and show a generic unavailable/error state. On patient/scope/session change, deselection, logout, panel destruction, or failed load, clear rows and invalidate pending results. Associate each asynchronous result with a request generation plus patient ID and scope; apply it only if it still matches the currently selected patient and current session scope. Do not cache or fall back to another visit, department, encounter diagnosis, or previous response. This implements the approved stale-data clearing rule (`docs/ke-hoach-trien-khai/phase1-tiensuben-scope-contract.md:25-26,30`).
4. **Create/update controls.** If the panel exposes the accepted history write workflow, offer only the three approved categories and use `SaveBenhNhanTienSuCommand`; create requests carry no client ownership scope, updates carry row ID and expected version. The handler supplies and validates ownership and audit. On save failure retain no success state; after success, reload using a fresh context so the read audit is written before showing the saved row. Never add delete or post-lock editing controls under this contract (`clinic-application/src/main/java/vn/clinicmanagement/application/patienthistory/SaveBenhNhanTienSuHandler.java:63-100,109-140`; `docs/ke-hoach-trien-khai/phase1-tiensuben-scope-contract.md:12-14,23-26`).
5. **Swing threading.** Make selection, clearing, table/model updates, and error/status rendering on the EDT. Do database/application calls in `SwingWorker.doInBackground()` and consume with `get()` in `done()` on the EDT, following the existing reception worker pattern (`clinic-desktop/src/main/java/vn/clinicmanagement/desktop/modules/reception/TiepDonManHinh.java:83-115,122-159`). The UI coding standard explicitly requires all UI updates on EDT and slow DB work in `SwingWorker` (`UI_CODING_STANDARDS.md:61`; feedback guidance at `UI_CODING_STANDARDS.md:520-524`). Cancellation alone is not a stale-data control; request identity/generation checks must prevent an older worker from restoring another patient’s data.

## Owner decisions — current state (2026-11-06)

The Doctor queue contract is approved: use the department/team queue for the selected exact facility+department pair, default to the current business date, and include only `CHO_KHAM`, `DANG_KHAM`, and `CHO_CLS`. Do not filter by provider assignment because `maBacSi` is not reliably populated. Do not include completed or cancelled visits in this active queue. The current reception SQL returns all non-cancelled statuses and needs a doctor-specific filter (`clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/reception/TiepDonHangDoiRepository.java:125-134`; `clinic-domain/src/main/java/vn/clinicmanagement/domain/common/enums/TrangThaiLuotKham.java:3-10`).

The queue decision does not change the existing `RECEPTION:XEM` gate, the history `DOCTOR` + `PATIENT:XEM` guard, exact-pair scope, approved categories, audit semantics or fail-closed behavior. No grant or scope widening is required (`phase1-tiensuben-scope-contract.md:9-14,22-26`).

**Separate unresolved rule:** post-lock history edits remain denied. `TienSuBenh` has no visit ID, while the current save handler does not check encounter lock state (`TienSuBenh.java:5-19`; `SaveBenhNhanTienSuCommand.java:8-16`; `SaveBenhNhanTienSuHandler.java:63-100`). Keep the Doctor UI read-only until an encounter anchor and server-side lock policy are decided and enforced. This does not block queue or history-read implementation.
