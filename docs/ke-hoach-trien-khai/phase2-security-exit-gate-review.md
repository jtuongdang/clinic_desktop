# SEC-GATE-EXIT-REVIEW-01 — Phase 2 security gate closure review

**Review mode:** Source-grounded, report-only proposal. Snapshot: 06/11/2026. No policy, grant, code, schema, database, test, or task status was changed by this review.

## Decision summary

**Transfer, billing exceptions, CLS, pharmacy, and inventory workflows are not necessary to prove the security foundation works.** Their role/action decisions are approved, but the approved decision record expressly keeps each workflow `DENY` until its own guard, audit, persistence, and tests are accepted. The Phase 2 roadmap currently lists transfer, billing-exception, and CLS/pharmacy/inventory work among what remains for `SEC-01`, while the board and roadmap also make `SEC-01` a prerequisite for those later workflows. That wording creates a **semantic dependency cycle** if `SEC-01` cannot close until downstream workflows are implemented. The graph does not need to be circular: treat `SEC-01` as a baseline gate, and each later workflow's own acceptance as its enablement gate. [Roadmap](02-cac-dot-trien-khai.md#L27-L43) · [Task-board dependency rule and SEC-01](03-model-task-board.md#L10-L10) [SEC-01 row](03-model-task-board.md#L58-L58) · [approved policy](phase2-role-permission-matrix-approval.md#L7-L26)

The recommended choice is **Definition A — Baseline security foundation** below. Preserve default-deny for all unimplemented workflows, require completion of existing-path security evidence and the outstanding UI smoke, and do not require downstream business workflows to be built. The Owner must explicitly decide whether the unresolved login-lockout policy is in this baseline or is deferred with documented risk acceptance; the review does not assume either outcome. [Lockout blocker](03-model-task-board.md#L84-L84) · [lockout proposal](phase2-login-lockout-policy-proposal.md#L1-L5)

## Evidence labels

- **Policy** means an explicit roadmap, implementation-contract, or Owner-approved decision; it does not prove runtime enforcement.
- **Implementation/test evidence** means source or a recorded test result for the named scope only; it does not prove every workflow or role is safe.
- **Inference/proposal** is the review's interpretation or a suggested measurable acceptance artifact, not an already approved policy.

## Viable gate definitions

### A — Baseline security foundation (recommended)

Close `SEC-01` when the trusted identity/session and default-deny evaluator are accepted; approved grants are limited to the approved matrix; the existing protected reception write/read paths pass role/scope, audit and SQL Server opt-in acceptance; the six-role matrix has explicit allow/deny tests for implemented paths and deny tests for unimplemented paths; and the required manual visual smoke is recorded. Keep transfer, billing exceptions, EMR, CLS, pharmacy, inventory, appointment deposit, audit-reader and administration workflows disabled/default-deny until each phase-specific task passes its own acceptance.

**Tradeoff:** avoids making a foundation depend on features it is meant to protect and lets the team verify a meaningful baseline sooner. It requires the Owner to explicitly settle or defer lockout and accept the bounded scope: the gate attests only to the enumerated existing paths, not all future sensitive operations.

### B — Comprehensive workflow security gate

Keep `SEC-01` open until every workflow in the approved role/action set (including transfer, billing exceptions, CLS, pharmacy and inventory) has its own end-to-end guard, audit, persistence, role-specific tests and UI acceptance. To avoid a cycle, Owner must authorize implementation and test preparation behind an enforced non-routable/default-deny boundary before SEC-01; no grants or runtime access are enabled until the comprehensive gate passes. Workflow enablement then requires its specific acceptance and a separate release decision.

**Tradeoff:** gives one broad “all named workflows accepted” milestone, but delays Phase 2 closure, substantially broadens the gate, and requires a deliberate dependency-model change; it risks conflating security foundation with later business delivery. It is not the current dependency interpretation and must not be adopted implicitly.

**Owner decision required:** choose A or B; decide whether login lockout is in-scope or explicitly deferred with risk acceptance; confirm that no future workflow is enabled by gate closure alone; and approve the measurable role-specific, SQL Server, and UI artifacts below. Until that decision, retain current `SEC-01` and downstream statuses and preserve all current denies.

## Proposed non-circular acceptance sequence

1. **Owner policy decision:** approve Definition A or B. Confirm the six role codes and approved role/action tuples remain authoritative; confirm `AUDIT_READ` remains denied and no audit purge occurs. Resolve lockout via option A/B/C in the lockout proposal, or explicitly document deferment and accountable risk acceptance. Do not treat decisions DEC-AUTHZ-04b/05/06/07/08 as grants. [Approval](phase2-role-permission-matrix-approval.md#L7-L26) [lockout choices](phase2-login-lockout-policy-proposal.md#L18-L44)
2. **Freeze the baseline test matrix:** enumerate every currently callable protected path and its allowed role/scope, invalid-role/scope denial, audit behavior, and error behavior. For all future/unimplemented workflows, assert default-deny and no data-returning path; do not add grants. Explicitly include six-role navigation coverage, and operation-level tests only for existing handlers. The approved role list and role-specific tests are defined by the approval and navigation/evaluator evidence. [Approval](phase2-role-permission-matrix-approval.md#L12-L18) [navigation implementation](../../clinic-application/src/main/java/vn/clinicmanagement/application/authorization/NavigationPermissionsHandler.java#L17-L75) [evaluator](../../clinic-application/src/main/java/vn/clinicmanagement/application/authorization/AuthorizationService.java#L34-L107)
3. **Automated baseline:** run the required root `mvn -Djava.awt.headless=true clean verify`; retain the exact test counts and opt-in skips. Confirm missing/invalid grants and dependency failures deny, no protected query occurs on denial, read data is withheld on audit failure, and mutation/audit rollback is atomic. The current roadmap reports the baseline as 243 tests, 0 failures/errors, 4 SQL Server opt-in skips; this is a dated snapshot, not evidence for the next run. [Roadmap](02-cac-dot-trien-khai.md#L10-L10) [board evidence](03-model-task-board.md#L58-L79)
4. **SQL Server opt-in, separately reported:** run the opt-in protected audit/grant/registration/read fixture only against an explicitly named synthetic `clinic_test_*` database; report database guard, migration start, V8 grant count/scope, live allow and deny cases, audit-failure rollback, successful-read audit, and cleanup. If the Owner chooses to require fresh-empty-database migration acceptance, run that separately; do not claim the existing V1–V7-to-V8 test is the fresh-empty path. Never connect to production or `clinicDb`. Existing synthetic test evidence and the not-yet-run fresh-empty case are recorded in [SEC-AUTHZ-03A-R2](03-model-task-board.md#L70-L70), [SEC-AUTHZ-03B](03-model-task-board.md#L71-L71), and [SEC-AUDIT-01D](03-model-task-board.md#L79-L79).
5. **Manual UI acceptance on an unlocked host:** record build/revision, operator, date, and pass/fail for role/scope selection; each role's visible modules; missing/invalid permission failure; lock/overlay, same-role re-auth, logout; and that denied modules/actions cannot be reached through UI. Keep this manual observation separate from Application/SQL authorization evidence. The visual smoke is still open; headless test completion does not close it. [Board](03-model-task-board.md#L60-L60) [roadmap](02-cac-dot-trien-khai.md#L36-L38)
6. **Owner acceptance and board update:** attach the evidence record, mark only the agreed SEC-01 acceptance items, and close `SEC-01` only after all selected criteria pass. A later workflow may be implemented behind deny after the baseline, but its grant, route, or use case remains unavailable until its own phase-specific authorization, audit, persistence and role-specific acceptance passes. Keep downstream status/dependencies unchanged unless the Owner separately authorizes a DAG revision.
