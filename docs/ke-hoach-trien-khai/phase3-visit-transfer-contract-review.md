# VIS-TRANSFER-REVIEW-01 — Visit transfer workflow contract review

**Status:** Report-only source review. Snapshot: 06/11/2026. No application code, tests, schema, grants, policy, database, or patient data changed or accessed.

## Executive finding

The approved DEC-AUTHZ-04b actor/scope rule is not implemented as a visit-transfer workflow. The only transfer-labelled desktop path is an examination-screen prototype: it confirms a transfer, chooses a hard-coded room label, and opens a print preview. It does not submit a visit ID or update a visit. Reception has protected room and queue reads plus registration, but no transfer action. Domain and schema hold the visit's current facility, department, and optional room, but no transfer history or transfer-specific mutation contract exists. No transfer command, handler, persistence adapter method, audit action, or transfer test was found.

The approved rules remain fixed: **RECEPTIONIST may transfer a visit between departments within the same facility; DOCTOR may transfer only within the selected department; transfer grants no patient read access in the destination department.** The workflow remains denied and gated by SEC-01. This review does not propose a grant or runtime enablement.

## Facts, approved policy, and inferences

**Facts:** Current visit stores one current facility/department/optional room and has a version column. Current reception registration writes a new visit and audit in a transaction. Reception queue reads and room summaries are exact facility/department scoped. The general authorization evaluator rejects target scope outside the session pair. The UI transfer selection is a string from a fixed list and only feeds a print preview.

**Approved policy:** A RECEPTIONIST can transfer a visit between departments in the same facility; a DOCTOR can transfer only within the selected department. Transfer does not authorize reading patient data in the destination department. Runtime remains denied until SEC-01 and the relevant implementation/test gates are satisfied.

**Inferences (not settled contract):** A safe implementation likely needs a narrow source-visit operation that resolves only the transfer facts needed for a decision, validates source scope and destination organizational ownership, mutates through an application transaction, and returns a minimal receipt. Any destination queue presentation that exposes patient identity would be a separate protected read and is not implied by transfer. Whether transfer changes the room, department, both, or queue placement is not established by current source or policy wording.

## Owner decisions still required before implementation

These are operational contract questions; none changes the approved actor/scope policy.

1. **Visit eligibility and state:** Which visit statuses may transfer? Are in-progress, completed, cancelled, soft-deleted, or EMR-locked visits eligible? Should there be explicit allowed transitions or other clinical/lifecycle guards?
2. **Destination room and queue:** Is a target department required to include a target room, or may the visit be department-assigned with no room? Must the room be active and belong to the selected target department and same facility? Does transfer retain, replace, or allocate queue number/display and priority? Which queue/date is used?
3. **Queue ordering:** Existing order is priority, queue number, ID for reception reads; should transfer keep that order, enter a new sequence, retain priority, or use another approved rule? Define collision/number allocation semantics without assuming the current registration algorithm applies.
4. **Time:** Define the transfer business-effective timestamp and date-boundary behavior. DEC-TIME-01 already sets technical/audit metadata to UTC and clinic business time to `Asia/Ho_Chi_Minh` ([`phase2-implementation-contract.md:8-12`](phase2-implementation-contract.md#L8-L12)); this review does not select a transfer timestamp field or queue-day rule.
5. **Orders and charges:** Should active service orders, prescriptions, billing/receipts, or other linked work block, follow, or remain at source on transfer? Current DEC-AUTHZ-04b does not answer this; do not infer constraints from unrelated cancellation policy.
6. **Audit reason and metadata:** Is a reason mandatory? Define bounded reason codes/free text, privacy limits, and the event payload (visit resource, source/target facility/department/room, actor role and scope, correlation/idempotency key, effective time, and relevant version) before implementation. Current audit writer's availability does not define these fields.
7. **Replay/idempotency and concurrency:** Define same-request replay result and conflicting second transfer behavior. Current schema has a visit `version`, but no transfer-specific compare-and-set contract; choose expected-version semantics, serialization/locking, and retry response. Do not assume generic transaction alone prevents lost updates.

## Concrete acceptance gates for a later implementation task

All tests use synthetic fixtures only. These gates do not authorize work before SEC-01 is accepted.

### Application and authorization

- A transfer command accepts an authenticated context from the application boundary, visit identity, destination identifiers, and the Owner-decided replay/version and reason data. It never trusts role, source scope, patient identity, or destination ownership supplied only by the desktop.
- Revalidate active session, employee, selected role and assignment. RECEPTIONIST: allow only when source visit facility equals session facility and destination facility equals that same facility; allow department change only within it. DOCTOR: require source and destination department to equal the selected session department and facility to equal the selected facility. Deny every other role unless a separate approved policy later says otherwise.
- Explicit tests deny cross-facility targets for RECEPTIONIST and DOCTOR, deny a DOCTOR target department different from session department, deny source visit outside the permitted scope, and allow RECEPTIONIST same-facility cross-department plus DOCTOR same-department cases. Test missing/revoked session, role, assignment, malformed IDs, and dependency failures as default deny.
- Transfer cannot call patient search, patient detail, history, or destination queue read. Verify denied attempts and instrumented fakes show zero such repository calls. A transfer receipt must not return destination patient/queue contents; destination reads remain separately authorized and audited.
- Eligibility and order/charge checks follow only Owner-decided rules and are revalidated within the transaction where required; no UI-only enforcement.

### Transaction, audit, persistence

- Resolve source visit, validate its current facility/department/room and expected version, validate target department/room relationship and active state according to the approved target contract, update the agreed location/queue fields, and append transfer audit in one `TransactionBoundary`.
- Audit failure must return failure and roll back every transfer/location/queue/history write. Persistence tests must prove no partial transfer and no success response when audit append fails (fail-closed atomicity).
- Record source and destination facts plus actor and metadata approved for the audit contract. Keep sensitive clinical narrative and unnecessary patient identifiers out of audit/log payloads.
- JDBC acceptance proves SQL predicate and bound keys enforce the approved source/destination scope, location relationships, expected version, and approved queue semantics; read back the persisted visit and any approved history after commit. If a schema change proves necessary, prepare a separate reviewed migration task; this report adds none.
- Replaying an identical idempotency key/payload produces the explicitly approved replay outcome without duplicate transfer/audit side effects. Reusing a key with a different payload is rejected. A stale expected version is rejected safely.
- A concurrent test runs two transfers against the same source version; exactly one wins and the other receives the specified conflict/retry outcome, with no lost update, mixed location, duplicate queue assignment, or missing/duplicate audit.

### Desktop and tests

- Replace/retire the prototype path only in a separately authorized implementation task. The UI must choose from scoped, persisted destination data, display only information authorized for the current role/scope, and call the application command; hiding controls is usability only, never the guard.
- Show a clear success/failure result from the application. On success, refresh only the currently authorized source queue/read model; do not automatically open or read the target department queue. Re-entry/retry follows the approved idempotency contract.
- Add focused domain/application/JDBC and headless UI tests for the role/scope matrix, cross-facility denial, no destination patient reads, eligible/ineligible states, target room/department consistency, transaction rollback on audit failure, replay, stale version, concurrent transfer, and success/failure UI feedback. SQL Server tests, if later required, must be explicitly opt-in and use a disposable synthetic database.
