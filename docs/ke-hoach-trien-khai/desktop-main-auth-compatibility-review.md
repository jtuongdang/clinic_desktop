## 1. Decision and scope

Do not replace current backend APIs with legacy overloads, first-role shortcuts or permissive adapters.

This task accepts the supplied approved contract v1 and the narrower report-only authorization. Only this Markdown file may change. No Java, UI, tests, configuration, data, migrations, application launch, SQL execution, push or PR is authorized here. ## 4. Candidate behavioral contract and invariants

This is the proposed contract to approve for implementation. It reuses existing backend contracts, introduces no grants/schema/role policy, and preserves default-deny throughout intermediate phases.

1. **Trusted identity and selection:** only the credential handler's successful result enters completion. `AuthenticatedUser` and `CompletedLoginSession` are public records, not cryptographic proof of authentication: production composition must prevent fabricated records or display setters from entering the trusted path. Completion does not re-verify a password. No direct startup from `new AuthenticatedUser`, mutable UI IDs or a test fixture is allowed. A future remote/untrusted API boundary would need its own proof-of-authentication contract.
2. **One role and one exact pair:** only select server-read assigned choices; no first-item fallback, role union, independent facility/department Cartesian product or “admin sees all” rule. [Repository assignment reads:186–231](../../clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/identity/NhanVienRepositoryImpl.java#L186) filter active/non-deleted employee, assignment and facility/department, and require department-to-facility relation. Keep `stationId/workstationId` separate from scope. Unknown roles do not gain an admin ribbon.
3. **Completion before activation:** [CompleteLoginSessionHandler:65–151](../../clinic-application/src/main/java/vn/clinicmanagement/application/auth/CompleteLoginSessionHandler.java#L65) matches selected choices against the immutable result, re-reads active employee/live assignments, and commits last-login plus `AUTH_LOGIN_SUCCESS` in one transaction. Audit failure prevents completion/activation. Use `CompletedLoginSession` as output, never re-create it in UI. Navigation/policy/lifecycle preparation must finish before session publication and dashboard visibility. Any failure clears pending context and leaves login usable. Completion audit commits before navigation loading in the prior flow; it records completion, not proof that a dashboard was displayed. A later navigation failure must not become a usable session or a duplicate automatic login retry.
4. **Navigation and action guards:** [NavigationPermissionsHandler](../../clinic-application/src/main/java/vn/clinicmanagement/application/authorization/NavigationPermissionsHandler.java) accepts only approved role codes and active unique `XEM` grants with `KHOA_PHONG`; empty/error/unknown/ambiguous grants fail closed. Use role **code** only to choose original doctor/general visual shell; use explicit grants to gate every button, dropdown child, default tab, keyboard shortcut, retained-tab activation and programmatic opener. No default/string-only constructor may fabricate identity. Unmapped report/admin/workflow routes remain denied. Hiding/disabling a button is only presentation.
5. **Application authorization remains authoritative:** [AuthorizationService:34–115](../../clinic-application/src/main/java/vn/clinicmanagement/application/authorization/AuthorizationService.java#L34) requires matching active/unlocked/unexpired session and context, active employee, current role/scope assignments, exact target pair and a unique allowed matrix row. Revalidate at each sensitive action, including direct calls with cached contexts. `AUDIT_READ` stays denied even for ADMIN; legacy broader scopes confer no access. Reuse guarded registration, patient search, queue and room handlers; legacy read constructors intentionally fail closed. A module grant never enables an unimplemented mutation, print/export or downstream workflow.
6. **Bounded lifecycle:** use configured [SessionTimeoutPolicy](../../clinic-application/src/main/java/vn/clinicmanagement/application/session/SessionTimeoutPolicy.java) with approved defaults of 15-minute idle and 12-hour absolute; missing/invalid/unavailable configuration cannot create an unlimited session. Do not hardcode timers as authority or silently widen the approved policy. Store issued-at, last-activity, absolute expiry and session ID. Anchor expiry to the accepted issuance time so slow navigation/worker startup cannot extend the absolute lifetime; prior startup uses its own clock rather than `completed.loginAtUtc()`, which needs an explicit test. Activity cannot unlock a locked/expired session or extend the absolute deadline. Use a fake clock in tests, not sleep.
7. **Lock/re-auth/logout:** lock shields all workspace content/input, popups, shortcuts and child dialogs while retaining drafts in memory; background jobs may not expose data behind it. Re-authenticate through the same real credential/throttle handler, require the same employee/role/exact pair still assigned, and commit re-auth success audit before unlocking. Wrong identity, revoked assignment, cancel or audit failure keeps the lock. Idle unlock retains the original absolute deadline; absolute expiry requires fresh authentication and a new bounded session ID, retaining drafts only for the same context. Changing identity/role/scope requires logout, draft warning and workspace disposal. Exit button, OS close and logout share cleanup: clear context even if audit fails, stop timers/listeners/jobs, destroy tabs and prevent stale worker completion from publishing data/session after lock/logout/replacement.
8. **Audit and failure:** real writers only; business mutations and their audit share one transaction. Protected successful reads audit before response; an audit failure yields no protected data. Denied operations stay denied even if failure-audit persistence is unavailable. Lock/logout must still block/clear locally during an audit outage; no exception may restore access. Re-auth success must await audit persistence. Address asynchronous lifecycle audit loss on immediate JVM exit with a bounded off-EDT completion/diagnostic path, without keeping a usable session alive or logging secrets. No audit purge or reader grant. Safe diagnostics exclude credentials, hashes, connection strings and record details.
9. **Existing throttle policy B stays intact:** account-wide SQL-authoritative state, fixed 15-minute window, five failures then 30-second delay doubling to 15 minutes, blocked attempts audit without verification/escalation, active-account successful password verification resets before role/scope checks, 24-hour sequence expiry. This is distinct from desktop idle/absolute locking. Do not add a lockout bypass or manual unlock; the older session contract's “lockout undecided” text is superseded by the [Owner-approved throttle decision](phase2-login-lockout-policy-proposal.md).
