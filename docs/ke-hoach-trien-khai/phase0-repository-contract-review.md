# Phase 0 — Repository contract-to-adapter review

**Scope:** source-level map of patient, visit, prescription, invoice, inventory, appointment, employee and system repository contracts in the current checkout. This review changes no Java, schema or migration files and does not connect to a database. “No adapter/use case/test found” means none was found in the checked-in source search, not that no external or uncommitted implementation exists.

## Assessment rules

The roadmap requires an end-to-end path from UI through application, domain and persistence, followed by a read-back and appropriate tests; an entity, panel or repository class alone is not completion evidence (`docs/ke-hoach-trien-khai/README.md#L19`, `docs/ke-hoach-trien-khai/00-hien-trang.md#L34-L37`). Accordingly, no row below is marked complete. “Partial” means only the explicitly evidenced behavior is wired and tested; it does not mean the model/workflow is complete.

The domain analysis describes repository contracts as JDBC-independent ports for infrastructure adapters (`DOMAIN_ANALYSIS.md#L44-L47`, `#L301-L314`). The Java sources are the authoritative contracts for this map. One documentation mismatch is material: the analysis describes generic `IRepository` methods as `findById/findAll/save` and says patient lookup includes insurance-card number, while the actual interface exposes `getById/getAll/add/update/delete` and `IBenhNhanRepository` exposes CCCD, phone and keyword search (`DOMAIN_ANALYSIS.md#L303-L314`; `clinic-domain/src/main/java/vn/clinicmanagement/domain/repositories/IRepository.java#L10-L20`, `IBenhNhanRepository.java#L6-L10`). Resolve the terminology/expectation mismatch before treating the analysis document as an adapter specification.

## Transaction semantics across the mapped flows

- `TransactionBoundary` is an application port (`clinic-application/src/main/java/vn/clinicmanagement/application/common/TransactionBoundary.java#L5-L8`). `JdbcTransactionManager` binds a connection to the current thread, commits a successful result, rolls back failed/null results and nested rollback-only work, and clears transaction/UoW state (`clinic-infrastructure/src/main/java/vn/clinicmanagement/infrastructure/persistence/JdbcTransactionManager.java#L10-L15`, `#L26-L66`). Its unit tests cover commit, rollback and cleanup with synthetic connections (`JdbcTransactionManagerTest.java#L20-L139`).
- Registration wraps patient, insurance and reception visit writes in one transaction (`RegisterPatientHandler.java#L39-L70`); `ReceptionCompositionRoot` shares the same transaction manager and connection provider across these adapters (`ReceptionCompositionRoot.java#L14-L24`). The existing SQL Server synthetic integration test is opt-in; its presence is not a result of this default Maven run. Project guidance likewise distinguishes transaction-boundary unit tests from multi-table SQL Server rollback evidence (`docs/ke-hoach-trien-khai/00-hien-trang.md#L35-L37`).
- Authentication places the successful-login timestamp write inside `inTransaction`, but account and role reads occur before it (`AuthenticateUserHandler.java#L31-L63`). No transaction semantics can be inferred for appointment, prescription, invoice, inventory or system workflows because no consuming use cases/adapters were found.

## Bounded implementation priorities

These are sequencing recommendations, not new business or access policy:

1. **Reconcile the written contract with the Java API.** Update the planned implementation contract to use the actual generic method names and narrow interface semantics; explicitly distinguish `ILuotKhamRepository` from the reception-only `ReceptionQueuePort`. Do not implement from the broader prose in `DOMAIN_ANALYSIS.md` without this reconciliation.
2. **Close evidence gaps on existing wired slices.** Keep the synthetic reception SQL test opt-in and run it only against its explicitly approved synthetic target when available; add focused SQL persistence coverage for employee authentication before treating the employee adapter as proven. Do not equate transaction-manager unit tests or handler fakes with repository persistence.
3. **Implement appointment and clinical visit lifecycle as one bounded roadmap slice.** Define the concrete use cases and persistence boundary for booking/slot conflicts and visit lifecycle, then add focused synthetic persistence tests for state transitions, reload and rollback. This follows the documented Phase 3 dependency and does not treat the reception queue insert as the full visit repository (`docs/ke-hoach-trien-khai/02-cac-dot-trien-khai.md#L33-L43`).
4. **Defer prescription/inventory and billing writes until their documented upstream gates are met.** Add only the adapters/use cases required by each agreed workflow and cover their critical multi-row transactions, read-back and failure paths with synthetic persistence tests. Follow existing phase dependencies; this review proposes no additional authorization rules (`02-cac-dot-trien-khai.md#L54-L67`).
5. **Treat system and employee administration as a separate bounded follow-up.** Add consumers and persistence tests only for approved configuration, audit and HR tasks; a repository class or system panel is not acceptance evidence (`docs/ke-hoach-trien-khai/phan-he/08-co-so-bao-mat-cau-hinh.md#L7-L31`).
