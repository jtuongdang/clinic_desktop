## Scope and conclusion

At the review snapshot, this was an analysis of the patient reception vertical slice and shared error types. No code or existing file was changed by that review task. The application already had a stable `Result<T>` with `success`, `failure(code, message)`, and `ApplicationError(code, message)`; its recommendations kept that contract unchanged (`clinic-application/src/main/java/vn/clinicmanagement/application/common/Result.java:6-39`).

At that snapshot, the duplicate active CCCD path was deliberately translated into a generic business error before it reached Swing. Validation and general registration failures also had user-oriented messages. The review identified inconsistent direct-message display and missing diagnostics at the reviewed boundaries. Later follow-ups added fixed-code registration presentation, redacted diagnostics for reception/authentication, and bounded UI error handling in the slices listed above. The remaining work is broader application-wide mapping and acceptance; those follow-ups do not complete `PLAT-ERROR-01`.

## Proposed bounded remediation sequence

1. **Keep the existing result contract.** Continue returning `Result<T>` and its stable code/message pair. Define a handler-level mapping inventory for known validation, duplicate identity, unavailable/not-found, persistence, and unexpected cases; do not add fields or change `Result` in this remediation.
2. **Make domain mapping explicit at application boundaries.** Preserve the current duplicate mapping. Add explicit mappings for known safe domain outcomes such as not-found and business-rule violations, with stable codes and user messages that do not include IDs, names, batch values, or raw exception text. Keep a final generic fallback for unknown failures.
3. **Add restricted diagnostics before details are discarded.** At the application or transaction boundary, log exception class, stack/cause, operation, stable result code, and correlation context. Redact patient identifiers and clinical payloads; exclude SQL message text and bind values. Avoid logging the `DomainException` formatted message where its arguments may include operational or patient-linked values. Do not send diagnostics to Swing.
4. **Constrain presentation to known result codes/messages.** In Swing, retain the duplicate dialog and masking behavior, display field-level validation text only for recognized validation outcomes, and use a fixed safe fallback for persistence/unknown codes. Avoid forwarding arbitrary `IllegalArgumentException` or `ApplicationError.message` text as a general-purpose safe display rule. Preserve current background work on `SwingWorker` and UI updates on the EDT.
5. **Verify the mapping with synthetic focused tests.** Cover pre-check and concurrent unique-index duplicate, field validation, empty search versus not-found, SQL persistence failure, and unexpected runtime failure. Assert the returned codes/messages are stable, diagnostics omit synthetic CCCD/phone/name values, and Swing-visible text contains no stack, SQL message, or unmasked identifier. This is a follow-on implementation/test recommendation, not work performed in this analysis task.
